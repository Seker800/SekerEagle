# 变更验证与返工刹车

## 三条硬规则

1. **单测、typecheck、源码字符串断言不是真实端验证。** 用户能看到的行为，必须在用户实际使用的端上走一遍。
2. **同一行为连续两次修复仍不通过，停止继续猜改。** 先写清根因和复现步骤，补一个修复前失败、修复后通过的回归测试，再一次改完。
3. **资源边界不得变成功能阉割。** 不按文件大小跳过能力，不按批次限制总量，不让用户手动拆批；优先流式、后台队列、自动分批。

## 按改动面验证

| 改动面                        | 必须验证                                                                                                                                                             | 证据                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 网页 UI、水印、编辑器、查看器 | `npm run dev --workspace @sekereagle/web` 后用真实浏览器走主路径和一个边界（空/错/慢/窄屏/深色）；查看器用真实大图走打开→放大→平移→旋转→再放大                       | 操作步骤、实际结果、截图或明确的视口与图片规格       |
| 桌面客户端                    | `npm run start --workspace @sekereagle/desktop`，验证窗口、登录、缩略图、查看器、连接状态；图标/深色外观在目标 macOS 或 Windows 上看真实 Dock/Finder                 | 启动端、系统版本、实际操作与截图                     |
| 安卓                          | 先 `npm run android:lab:status`，需要固定图库时 `npm run android:lab:preview`；构建与设备检查用 `npm run android:check:device`；平台 API 在目标 Android 版本实机验证 | 设备/模拟器版本、固定图库地址、操作结果              |
| 上传、入库、后台任务          | 真实文件大小（含 RAW/HEIC/大视频）；确认请求线程不读整份原图；`npm run test:library-integration`；涉及镜像时 `npm run test:api-image -- <标签>`                      | 峰值内存、任务归属进程、端到端一批的 SQL/S3/事务次数 |
| 数据库迁移                    | 在隔离库跑 fresh migrate deploy；检查旧快照可读、隐私与删除路径；确认回滚边界                                                                                        | 迁移编号、前后数据不变量、回滚说明                   |
| 架构拆分/移动                 | `npm run architecture:check`、`npm run test:architecture`；启动受影响进程（API/operations/worker/desktop）并走一条真实路径；同一提交更新门禁目标和反例测试           | 启动日志/健康检查、真实请求结果、门禁反例            |
| 发布脚本/部署                 | `npm run deploy:mac:check`；生产脚本先 preflight；用失败注入覆盖回滚；禁止只用“前后计数完全相等”作为放行条件                                                         | preflight 结果、失败注入场景、回滚验证               |

## 返工刹车

改一个最近动过的文件前，先看它最近 24 小时：

```bash
git log --since="24 hours ago" --oneline -- <文件>
```

出现以下任一情况，停止直接改代码：

- 同一行为已经连续修了 2 次还没通过；
- 同一文件 24 小时内已有 2 次“修复”；
- 你正准备用“再试一个假设”的方式提交。

停下来做三件事：

1. 用 3 句话写根因：真实端看到什么、代码为什么这样、上次假设错在哪。
2. 补一个回归测试：修复前必须失败，修复后必须通过；UI 用真实事件序列，数据库用真实数据库，门禁用反例。
3. 一次改完再验证，不把验证拆成多次提交。

## 提交证据

提交说明里写清：

```text
验证：<端> <操作> <结果>
未验证：<项>（原因）
```

没有真实端证据时，不要写“已修复/已完成”，写“未验证”并说明缺哪一端。发布记录只写实际跑过的验证，不把单测通过写成功能验收。

## 禁止

- 用单测、typecheck、源码正则断言代替真实端验证。
- 未复现就连续提交 3 个猜测。
- 用新上限、跳过预检、请求内全量解码代替流式或后台处理。
- 移动被门禁守护的文件后，让门禁静默跳过或继续检查旧路径。
- 把“前后计数完全相等”当成发布唯一放行条件。
