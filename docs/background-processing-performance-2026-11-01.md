# 后台处理性能修复（2026年11月1日）

> 后续发布：2026-11-01 用户授权后，本文候选已随固定源码 df6d3688305a 配套上线；生产版本、成品验收、两端检查、保护与回退见[效率生产发布](production-efficiency-release-2026-11-01.md)。下文的“本地候选／未部署”保留为实施阶段记录，不表示最新运行状态。

本轮由用户反馈“清理重复项很慢”，随后明确要求解决新功能反复引入慢后台的问题。目标是让业务能力复用高效的处理流程，而非继续增加各自的删除、事务与回执实现。本文件记录本地候选，不表示已经部署。

## 现场证据与原因

只读核验现用 API、网页和独立 operations 为 `release-727ef115cf2e`。北京时间10:47左右，素材清理约14分钟仅完成374／957份，照片清理约12分钟完成537／1014份，无失败。现场数据库约170% CPU，多条后台候选查询运行5～7秒，多次见到 WALWrite／WALSync 等待；这些是采样，不是完整请求剖析或p95。

查重清理原先每次只领取一组，每组单独提交。普通删除已有32项元数据批次，查重没有复用这一执行单位。两者虽然调用同一 `setEagleTrash`，外层事务、守卫和回执仍有重复编排。

另一个共用负担是独立业务worker每次唤醒执行失败依赖传播。现场约45.6万任务，其中约11.9万待处理任务没有任何依赖；约6.1万失败记录主要是已退役功能。旧执行计划仍并行扫描待处理集合，并读取失败历史及递归连接。共享缓冲128MiB、资源表连索引约474MB、任务表连索引约356MB，是放大竞争的背景，不据此认定缓存大小本身就是根因，也没有改数据库缓存、持久化或用户调度。

以上能够证明共用执行路径存在浪费，不能证明全部页面、搜索、上传或编辑卡顿都由这两处引起。

## 共用边界

- `EagleAssetOperationService` 继续唯一负责持久队列、领取、租约、失败隔离、重试、取消、撤销和回执。删除、恢复和查重清理统一通过 `publishMetadataBatch` 完成权限、隐私锁、业务事务及终态发布。
- `EagleDuplicateService.applyCleanupBatch` 仅提供保留项版本、实况组件、标签与评分合并等业务规则；回收仍调用原 `setEagleTrash`，没有第二套删除实现。
- 正常查重清理复用 `EAGLE_OPERATION_METADATA_BATCH_SIZE`（默认32）。这是既有数据库持锁与执行工作量配置，整笔用户选择自动继续，不需要手动拆批。既有45秒事务预算保持；超时批次先完整回滚再逐项执行，仍超时的单项保留原错误回执。没有提高并发、放宽安全边界或新增产品配额。
- 失败依赖传播保留原递归规则与owner／模式连接，查询显式选择有依赖的待处理项，配套部分覆盖索引排除独立任务与已退役历史。索引维护随真实待处理依赖边发生，不为每次唤醒扫描全表。
- 发送与扫描继续共用队列，但对象移交journal、外部计算及有界原图解码具有不同的发布／资源要求，不放入通用元数据持锁事务。前端本轮未改变，不增加轮询或列表刷新。

## 成本与回归

本机隔离PostgreSQL16、合成资源，不是NAS、HTTP或p95。32组各两份资源的整轮执行含领取：素材2事务／471SQL／287.69毫秒，照片2事务／439SQL／254.47毫秒，S3为零。原实现一轮仅处理1组；没有在现场执行重复的真实删除做对照。千组的正常领取与发布事务由代码推算从约2000笔降到约64笔，不是生产提速倍率。

每组仍保留快照、实况、标签、评分和权限投影等SQL；本轮没有声称全部SQL已按集合摊销。32组测试同时要求2事务、最多512SQL和零对象读取，避免重新退回逐组领取或无意增加SQL。冲突时整批回滚后逐项隔离，最坏成本增加，健康项不因同批冲突丢失；任何授权、版本和租约失败仍禁止发布。

失败传播的24000项隔离队列含12000份独立待处理与12000份失败历史，旧查询2224次数据库块访问／25.801毫秒，新查询2次块访问／0.027毫秒。断言要求无待处理依赖边时少于64次数据库块访问，不要求固定毫秒数；另验证多级依赖传播、独立工作保持及幂等重查。组合测试中使用带相同迁移索引的临时队列表隔离该场景，避免前序夹具的依赖和索引死条目影响零依赖假设；数据库块预算同时统计共享与本地缓存，不借临时表改变计数口径。

查重测试、普通删除／恢复批次与部分失败测试、六万项选择、调度性能测试已在原 `scripts/testing/run-library-tests.mjs` 中执行；GitHub CI的 `test:library-integration` 会运行它们。不能用单测通过替代这条真实数据库门禁，也不能把成本断言理解为任意新功能都不会回归。

## 发布范围

候选增加 `20261101020000_pending_media_dependencies` 索引迁移，无数据回填、删除或对象存储修改。尚未push、部署、迁移现用数据库、暂停用户任务或改变计算策略。发布前仍需最终API成品镜像验收、备份／部署授权和配套独立operations／业务worker更新。运行状态以 `current-runtime.md` 为准。

`npm run ci:check`通过，包括架构与共用契约、lint、typecheck、unit、build、生成契约差异、格式和开源清单。最后单独调整的集成夹具另经ESLint、格式与完整组合复测。查重专项27项通过；操作执行器在完整真实数据库组合中的行／分支／函数覆盖率为97.50%／87.29%／94.69%。六万项一次入队、批次部分失败、隐私／主体／版本／租约、撤销与恢复、独立执行进程均通过。

完整 `scripts/testing/run-library-tests.mjs` 在显式指定本仓库 `.runtime/compute-tools/media/bin/ffmpeg`、`ffprobe` 后通过：独立视频、图片、金字塔和向量计算，动态策略排空／恢复与正常退出通过；历史升级和完整数据库备份恢复后，所有业务表摘要一致。此前未指定ffprobe的测试进程在远程视频步骤返回500，属于本机测试工具路径问题；没有因此跳过验收或修改业务行为。

新增性能样本最终为32组素材471SQL／2事务、照片439SQL／2事务，零S3；24000任务的失败传播2次数据库块访问。全部为隔离合成样本，没有对真实用户资源重放清理，也没有测量新候选的NAS生产收益。项目 `AGENTS.md` 已要求后续新增后台批量元数据能力复用该流程并验证入队及执行成本。
