# 编辑成片保存事务与失败恢复

2026-11-01。用户反馈调整照片后点击保存，出现 `Internal server error` 和“重新加载”，此前已有一次修复。

## 根因与检查范围

此前修的是对象存储签名 Host 不一致造成的 PUT 403。本次在现用 API、网页和网关上，隔离合成主体的素材保存成功；照片保存时仅持有该测试主体的隐私一致性锁 6.5 秒，即可复现 HTTP 500 / Prisma P2028。发布事务没有指定预算，采用 Prisma 默认 5 秒；等待保护原图和私密继承的锁也计入事务时间。失败后同一上传会话再次完成可成功，说明图片上传和数据库发布是两个不同阶段。

生产原有日志还包含一次 5 秒提交超时，但对应会话已清理，不能证明它就是用户的那一次请求。锁竞争复现是可验证的同类失败机制，不宣称找到了已消失请求的全部现场原因。编辑器初始化方面，真实 Electron 只读打开一张 JPEG 正常；未修改或保存这张用户照片。

共享编辑器把保存错误与图片加载错误共用“重新加载”，点击只重建预览，并不重试保存。另有跨进程完成竞态：前台读取未完成会话后等待锁，后台已发布时，前台仍校验冻结的旧来源或报告 409，可能被界面当成来源失效；暂时的事务错误还会消耗最终失败次数。

本轮额外核对数据库与存储：NAS 剩余约 46 TB，未见磁盘满；只读快照中一项已运行约 12 分钟的 `EagleMediaJob` autovacuum 处于 WALWrite 等待，另有备份读取 IO。存在 I/O 压力迹象，不能把任务总时长都算成等待，也不能据此断定旧请求的唯一根因；本任务没有暂停维护、降低持久化保证或修改用户处理策略。

## 修复边界

- 唯一共享上传发布事务采用默认 30000 毫秒预算，`EAGLE_UPLOAD_PUBLICATION_TIMEOUT_MS` 可调整，要求正安全整数。保护的是数据库连接与隐私／资源锁的占用时间；预算不包含原图上传、S3 检查或图像检查。事务内用 LOCAL statement_timeout 为实际 SQL 提供同一预算，避免仅 Prisma 计时到期而仍无限等待锁；连接归还后该设置不保留。到顶回滚，返回具名 503，保留已上传对象供重试，不新增用户数量限制。
- 临时事务过期、连接池等待、事务冲突或 PostgreSQL 57014 语句取消不消耗永久恢复失败次数，不把临时繁忙推进到对象清理。其他错误保持原处理。
- 保持先隐私锁的跨进程顺序；认领失败时按同主体、同模式读取已完成会话并返回原副本，不再校验旧来源。不改变原片版本检查、私密标签继承、跨 owner 404 或发布事务原子性。
- 显式 CREATE_COPY 不做哈希去重，去掉对应的无效哈希互斥锁；普通去重导入仍保留原哈希锁。
- 保存失败提供“重试保存”，沿用同一个 File 和上传会话；加载失败仍重新加载，定位成片失败重试定位。中英文客户端按稳定错误码说明已上传但保存暂时繁忙。

无迁移、没有新增队列／provider／模式分支，摄影元数据和照片组继续走既有修订观察者。

## 成本与资源

以下为代码路径推算，锁等待耗时另有上述实测，不将小合成图当作真实大图 p95：

- 单次保存沿用一份副本、一个原发布事务。正常 CREATE_COPY 减一条哈希锁 SQL、加一条事务本地语句预算 SQL，净变化零；普通去重导入只增加后一条 SQL；只有认领竞争失败分支增加一次按会话／主体／模式读取。未增加普通分页或轮询，成功仍按原资源／标签查询键失效。
- S3 正常路径仍为一次 multipart 创建、每个分片一次 PUT、一次完成、一次 HEAD 和一次检查 GET；浏览器按需读取原图另计。数据库事务内没有 S3 IO。
- 暂时失败后重试使用同一个已组装对象，不重新创建上传会话、不重传已成功分片；服务端仍需一次 HEAD、一次检查 GET 和一次发布事务，不能说完全没有重复读取。前端不重新下载原图或编码已有成片。
- 批量套用仍使用既有逐项队列；本修复不提高并发、不新增产品配额，不修改现用任务暂停、时段、模型或计算策略。
