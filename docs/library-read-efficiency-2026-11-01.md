## 改了什么

独立的 `library-reader` 进程集中加载常用元数据。API 继续负责登录、私密访问和当前页投影；数据库仍是业务事实来源。两个模式分别维护索引，查询由 API 的认证主体确定 owner，读取服务不接受公网请求。

普通列表、普通智能规则、语义组合规则、颜色排序、计数、人物照片数、照片统计以及相机／镜头选项可复用这些信息。没有为特定文件夹名称、ID 或某条已保存规则添加捷径。未支持的输入、读取服务故障、超时或修订不一致，都保留完整数据库路径。

借鉴的是本机 Eagle 4.0.0 已核实的预加载数组、规则短路和标准排序。语义分数、颜色算法、统计 SQL 与排序契约来自项目既有实现；没有新增向量副本、位图、推理算法或条件自动重排。语义匹配在请求内读取既有持久结果，模型未完成时继续保持未就绪语义。

## 更新与一致性

- 语句级触发器在原写事务中登记受影响 ID；一个批量更新登记一个批量事件，不增加逐项业务事务。
- owner／模式修订行与提交绑定，解决“较早开始、较晚提交”的遗漏。即使读取尚未启用，也维护小型修订计数；关闭时并非零写入成本，但不累计 ID 日志。
- 独立宿主每秒检查小型修订表，API 进程没有轮询；触发器只登记持久变化，不额外发送无人消费的通知。
- 读取进程在一致性事务中批量加载并同步发布；查询不会看到更新到一半的索引。语义查询只复制一份 ID 到行对象的引用表，更新发布新行对象；等待数据库时可保留原查询代次，不因无关后台变化退回整库 SQL。已提交的修改在下次同步中可见，事务回滚不会产生虚假变化。
- 热查询先读修订；变更只按受影响 ID 重读八类信息。标签改名展开实际关联资源，不重建整库。普通字段更新不重排日期，颜色或标签更新不重算不依赖它们的统计。
- 首次加载、重启、日志缺口均从事实表重建；发布成功后才确认日志。语义查询在同一数据库事务内追赶必要的元数据，再读取匹配，避免后台写入造成不同代次混用。
- 返回候选仅包含当页 ID／排序位置；API 沿用原可见性和条件读取卡片。并发变化丢失候选时回退原路径，避免把不完整页当作终点。签名和缩略图继续使用原流程。
- 暂未新增磁盘快照文件。数据库已经集中保存信息；隔离夹具初建曾为 451 毫秒，完整回归负载下为 9.03 秒。初建在独立进程中完成，API 保留原查询；磁盘快照暂不引入，是否需要应由部署后的重启实测决定。

## 性能证据及口径

### 本机合成读取信息，127549 条／两模式

Node 22.22.3，Mac arm64，640 MiB V8 堆设置，100 次暖查询；含基础、标签、注释、摄影事实、人物关系和颜色对象。以下是进程计算，不包括数据库、API 鉴权、网络、缩略图和 NAS 磁盘等待。

| 项目                             | 实测         |
| -------------------------------- | ------------ |
| 加载并预排序                     | 384 ms       |
| 进程 RSS／峰值 RSS               | 365／498 MiB |
| 普通首屏计算 p95                 | 0.05 ms      |
| 无相机命中，扫描完整两模式 p95   | 32.14 ms     |
| 无颜色命中，扫描完整两模式 p95   | 34.70 ms     |
| 无标签命中，扫描完整两模式 p95   | 50.29 ms     |
| 建立查询快照并扫描完整两模式 p95 | 48.86 ms     |
| 相机否定条件 p95                 | 41.69 ms     |

包含快照的完整扫描 p99 为 163.69 ms，存在垃圾回收停顿；p95 不能代表最慢一次。未设置部署堆预算时，同一批连续查询曾达到 731 MiB，因此上述峰值必须连同 640 MiB 堆设置理解；不能把堆预算当作总 RSS。连续颜色查询曾暴露临时字符串分配导致 RSS 接近 1 GiB；已将颜色组合标识提前到加载阶段准备，复用原分数且限制可选计算缓存。不得仅引用最初不含连续颜色查询的内存结果。

### 隔离 PostgreSQL，六万条整批元数据更新

早期独立夹具初建 451 ms、进程 RSS 515 MiB；最终完整数据库回归的同规模初建 9029 ms、RSS 480 MiB，两者负载不同，不作固定冷启动承诺。最终两轮相同批量更新，基线关闭本轮资源更新记录触发器：6053／6228 ms；开启：6265／6508 ms。单次增加约 3.5%～4.5%，仍有缓存与负载噪声；新增记录并非零开销。完整无匹配扫描 p95 为 25.39 ms，仍只指计算。

每轮恰好一个派生事件，包含完整六万个 ID，零额外业务事务。另修复原回收任务触发器在没有任何资源进入回收站时仍关联整批新旧行的问题；修改前同一规模超过 180 秒并触发测试语句预算，修改后原整批约 6～8 秒。真正进入回收站的发布、任务失效与租约保护保留。

### 后台唤醒

独立待办与需要依赖检查的待办分开读取，复用现有待依赖索引，避免没有依赖的任务触发历史依赖扫描。隔离夹具 12000 个待办＋36000 个历史任务，访问任务行从 60000 降到 12000，33.36 ms → 27.35 ms。

群晖只读、相同事务快照对照：原查询 1881.89 ms，候选 920.96 ms；两个方向 EXCEPT 差异为 0。原路径共享块命中／读取 35291／16714，候选 7649／9846。该样本没有修改生产部署、暂停、模型或任务；冷热顺序仍会影响时间，不外推为全部请求的固定收益。

## 资源预算与运行

使用 `deploy/mac/docker-compose.library-reader.yml` 显式叠加，读取服务仅在 Compose 内网，不发布端口；同一 API 成品镜像运行独立入口。服务数据库 URL 和令牌由私有配置提供，仓库没有部署凭据。

| 环境变量                                    | 默认     | 保护资源／到顶行为                                                         |
| ------------------------------------------- | -------- | -------------------------------------------------------------------------- |
| `EAGLE_READER_MEMORY_LIMIT`                 | `1g`     | 进程 RSS；容器异常时 API 继续数据库路径，读取进程重建                      |
| `EAGLE_READER_HEAP_MB`                      | `640`    | V8 堆，包含常驻与临时对象；与容器总边界配套                                |
| `EAGLE_READER_QUERY_WORKSPACE_BYTES`        | 128 MiB  | 请求内语义匹配图与引用表快照；到顶返回能力不可用，API 完整回退，不截断结果 |
| `EAGLE_READER_COLOR_CACHE_BYTES`            | 8 MiB    | 单次颜色计算的可选复用；到顶继续计算，0 可关闭，不减少结果                 |
| `EAGLE_READER_REQUEST_MAX_BYTES`            | 2 MiB    | 内网查询解码内存；超出后 API 完整回退                                      |
| `EAGLE_READER_DATABASE_CONNECTIONS`         | 2        | 数据库连接与并行读取空间；请求等候连接，达到连接等待预算后完整回退         |
| `EAGLE_READER_CONNECT_TIMEOUT_MS`           | 3000 ms  | 新连接／连接池等候；超时完整回退                                           |
| `EAGLE_READER_DATABASE_TIMEOUT_MS`          | 60000 ms | 初建及追赶读取的数据库语句；超时回滚，不发布半份索引                       |
| `EAGLE_READER_SEMANTIC_DATABASE_TIMEOUT_MS` | 5000 ms  | 单批语义匹配的数据库占用；超时回滚，API 完整回退                           |
| `EAGLE_READER_SEMANTIC_BATCH_SIZE`          | 2048     | 每批临时解码空间；自动继续读取后续批次，无总结果上限                       |

上述不是素材、规则或用户操作的数量配额。连接池默认两个并发连接，语义工作空间按请求计算；总内存边界包含同步与查询峰值。新旧完整索引或大规模变更可能增加瞬时内存，成品验证与实际容量监测仍须覆盖，不能只看稳定对象体积。

## 2026-11-02 常驻读取修订（本地候选，未切换生产）

用户要求常用信息提前驻留，查询直接使用内存，后台只刷新变化部分。线上只读核查确认旧实现每次查询先等待 `synchronize`；颜色同步曾出现超过10秒的数据库读取等待。API原客户端四次普通列表探测中三次超过200毫秒预算回退，一次命中为14毫秒；一次语义探测超过1000毫秒回退。这是诊断采样，不是命中率或p95统计。

新前台入口与后台同步分离。无变化时只读一条owner／mode提交修订，不复制六万行引用、不等待后台任务；有变化时，从已发布的不可变版本定向追赶，并与后台单调发布。并发读者完成之前保留其需要的日志；隐私、删除、新增和规则修改没有通过允许旧计数或跳过当前页权限来换取速度。冷启动未就绪及时返回原SQL路径，由独立宿主继续准备。

原变更日志补充来源表与语义文件夹ID。颜色变化只刷新颜色；标签、人物、注释等关系直接限定自身owner／mode及资源ID，避免只靠连接主表过滤导致全表扫描。旧线上只读SQL对照中，32项／133条相同标签结果，原查询89.6毫秒，使用现有作用域索引的查询1.9毫秒；冷热和负载不同，不能把该单语句倍率冒充完整页面提升。

语义成员、媒体版本和分数现在在快照准备时加载；热查询不再开启语义数据库事务或重读匹配集合。活动快照切换、匹配分数修改／删除、关联向量的版本／状态变化，在原业务事务内交给同一提交修订流；未激活的构建过程不反复刷新已发布成员。原始1024维向量、模型权重及图片仍不进入内存读取服务。目录定义仍由原API读取，当前页卡片仍保留原权限与筛选投影。
