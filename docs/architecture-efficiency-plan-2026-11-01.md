## 1 目标与执行约定

本轮目标是让同样的用户操作减少数据库查询、事务提交、文件读写和前端重取，让核心结果更早可用，同时使新增功能必须复用已有的高效执行协议。职责划分服务于这个目标，不能把拆文件、加接口、统一命名或增加异步任务本身当作提效成果。

用人话说：各能力负责自己的业务，公共执行规则只维护一份；少做重复工作，能按集合处理的按集合处理，必须立即保证的正确性立即保证，允许延后的收尾可靠地在后台完成。

本计划整合重复逻辑审计、图片与向量职责讨论、后台批处理建议及后续范围确认。它是后续实施的约束，不表示这些改动已经实现、验证或上线。初次交付只新增计划文档。随后用户已明确授权“按照计划帮我做架构优化”，本地实施与逐项采用／保留决定见[实施验收记录](architecture-efficiency-results-2026-11-01.md)；本计划及该本地授权均不表示已部署，不授予生产操作权限。

适用规模是一个 owner、约六万份照片或素材、单张最高6100万像素，API 单实例、NAS 数据库和对象存储、Mac 业务 worker。默认验收网页与桌面；安卓不是本轮新增范围。优先级沿用不丢数据、不越权、不泄露、结果正确，然后才是吞吐与延迟。

## 3 必须保持的不变量

### 3.1 业务和数据边界

1. 素材与照片导入托管、业务隔离；不引入双重归属、外部目录图库或仅前端过滤。
2. ownerId 由认证主体推导，模式由装配固定；跨 owner 404，DTO 不接受 ownerId。私密授权、当前版本、模型身份及租约在领取和发布所需边界继续复核。
3. 原图不可变；编辑生成独立成片。原件替换使旧版本结果失效，旧执行者不得迟到发布。
4. 普通删除可恢复。向量、标签关联、编辑事实等有恢复价值的信息不因为进入回收站就立即物理删除。标签本体与单张图片的标签关联不是同一资源。
5. 永久删除先可靠登记清理意图，再按现有事务和outbox清理；数据库失败回滚，S3失败幂等重试。数据库已级联处理的子记录不重复手工遍历。
6. 发送创建独立目标并在同一发布事务内退休源项、移交对象；源不进回收站。已移交对象不进入源项对象删除清单。
7. 去重保持至少一份保留项；标签及最高评分合并、隐私重算和回收保持业务原子性。不同输入之间共用的实况组件不得被拆开清理。
8. SekerChat 完全不在范围内，不读取或修改其文件、运行时、数据库、对象存储、Cookie或secrets。

### 3.2 执行和资源边界

1. API 负责认证、受理、持久化和查询。后台业务由独立进程或既有队列执行，不放入API定时器、未等待Promise或请求结束后的内存回调。
2. 不复制原任务事实表。展示、候选缓存和事件只是事实投影或唤醒提示，不能成为另一份可调度队列。
3. 既有用户暂停、时段、owner、模式、模型兼容、资源版本、租约和人工审批保持。暂停一般限制领取，不强杀已经领取的安全收尾。
4. NAS、模型、远端节点、API上传检查、operations解码和对象删除分别保护真实资源。不得用parallelMap或万能线程池统一所有并发。
5. 内部分批自动继续，不新增用户可见选择数量上限；不要求用户手动每几十张再提交一次。
6. 新增或调整内部预算必须写清资源对象、内存和磁盘规模、到顶表现、配置来源及恢复方式。用户看到等待或明确可重试失败，不静默漏项。
7. 进度不重置前端页数、滚动、选择、未保存草稿；最终结果不能因少刷新而残留错误卡片。

## 6 工作包与验收

### W0 建立可重复的成本基线

对应E03、E04、E07至E15。先记录实际源码提交、已有改动、测试夹具及现用发布版本的区别，不将本地候选当线上现状。

1. 用现有隔离数据库测试入口准备合成资源，覆盖MATERIAL和PHOTO。测试前运行安全目标检查；不连接真实图库做破坏性对照。
2. 将一个用户操作拆成认证／准入、领取、业务发布、附加任务、物理收尾、状态轮询和终态刷新；各段计数，再给总量。
3. SQL按真实query事件统计，明确是否包含BEGIN／COMMIT。清空、缓存、并行日志需要在测量窗口前后排空；不能把上一阶段异步日志算到下一项。
4. S3分HEAD、GET、PUT、COPY、DELETE、LIST及multipart；记录模型请求次数、读取字节、解码次数、RSS、临时文件峰值、锁持有及等待、WAL／索引工作。
5. 同一机器、数据、并发、模型和存储位置对照；先预热，再交替跑前后版本。计数用确定性门禁，耗时使用多样本分布；少量样本不称p95。
6. 基准至少覆盖删除500项、清空500项及六万项、去重32组和千组、发送100项、向量单项和持续队列。增加共享标签和多派生产物夹具，不能只用空记录。

既有基线只作参照：[性能修复记录](background-processing-performance-2026-11-01.md)记录32组执行含领取为PHOTO439／MATERIAL471 SQL、2事务、零S3，当前门禁为最多512 SQL。它不含完整HTTP准入、认证、前端刷新及物理清理，也不是本轮新测值。先前聊天中的删除497条等为特定假设下的源码模型，不作为承诺或CI阈值。

验收：每个准备修改的热点都有机器可读取的前后结果和夹具说明；缺失计数标为未测并说明具体缺口。不能用“看起来更快”替代基线。

### W1 封闭操作类型和公共执行协议

对应E04、E05。改动入口包括 `eagle-asset-operations.service.ts`、kind契约、DTO、操作面板和前端操作投影。

1. 用穷尽类型登记六种现有kind，显式声明准入入口、快照类型、执行协议、回执语义和补偿资格。禁止新增kind自动进入直接操作DTO，禁止未处理类型落入回收else。
2. 保留同一持久operation／item和现有执行器。元数据处理器接收受授权批次及现有事务，不自行领取、开事务、重试、写完成状态或复制权限检查。
3. 发送处理器继续拥有journal与目标／源发布协议；扫描继续分阶段外部计算；EMPTY_TRASH保持cutoff语义。它们不套入持锁的元数据事务。
4. 执行器继续统一完成前后主体／私密／租约检查、作用域一致性、终态回执、冲突回滚及逐项隔离。
5. 前端按kind穷尽登记显示及成员变化语义；未知持久kind显示明确不可执行状态，不能默认成“清空回收站”。

接口方向，不规定为了接口新增目录或包：

```ts
type OperationHandlers = { [K in AssetOperationKind]: HandlerFor<K> };

applyMetadata<K extends MetadataOperationKind>(
  tx: Prisma.TransactionClient,
  batch: AuthorizedBatch<K>,
): Promise<MetadataOutcome>;
```

`HandlerFor` 按元数据、发送、扫描、清空请求区分协议，不是一个包含十几个布尔选项的万能执行器。领域登记不允许改变owner或mode。

验收：新增kind但漏登记编译失败；绕过类型写入陌生kind的数据库用例不修改任何资产；原六类完整回归；结构迁移对相同操作的SQL、S3、事务和HTTP计数零新增。原32组两事务门禁保持。

### W2 统一数据库分批预算而非业务循环

对应E06，十二处位置列于附录A。抽的是完整遍历、稳定offset及数据库参数预算，不是 `chunkAssets()` 业务函数。

```ts
databaseBatches<T>(
  rows: readonly T[],
  statement: DatabaseStatementBudget,
): Iterable<{ offset: number; rows: readonly T[] }>;
```

语句预算由持久化适配实现登记，至少区分固定参数、每行绑定数和已有执行工作量目标。数据库参数约束只有一份；实际批量按语句安全容量及已有内部批次策略取值。不同语句的行宽不是不同产品策略，不把任意size数字继续散落调用处。

1. 默认512不等于所有语句的上限。现有floor(32767/12)不能盲目用于14列或更多绑定的createMany；以真实生成SQL和参数验证登记。
2. 数组绑定和逐ID IN展开分别计算；实况展开后的资源数量、恢复时的复合OR、固定owner／mode条件都要计入。
3. 保留createMany的全局ordinal、阶段偏移、集合去重、事务边界及skipDuplicates语义。
4. 保留清理执行前的版本比较和每批回收前的实况重检。不能因共用迭代器就删除重复读取；先证明保护的是同一个竞争窗口。
5. 不改变用户选择规模，不加入手动分批。默认500改512只算配置收拢，不声称性能提高。

验收：空集、1项、边界前后、六万项、宽行、固定参数和实况展开均不漏项；两个ordinal序列保持；每种登记在允许配置边界下都不超过实际参数预算。仅替换迭代方式时SQL数量不得增加，业务结果与原实现等价。

门禁：在明确覆盖的数据库批处理路径用AST检查禁止新增裸500／512业务切片，登记新语句必须附真实数据库边界用例。避免全仓粗暴禁用数字，S3协议分片等不在此规则内。

测试：查重单测和集成、operations大选择、原图核验阶段恢复、共享门禁及其反例。

### W5 分开向量发布与附加处理的恢复责任

对应E08，依赖W0、W4。智能文件夹匹配和标签建议现在是明确的事务耦合；它们是否都应成为独立任务取决于成本和可接受的结果可见性，而非“事件驱动更高级”。

先比较两种可行方案：

| 方案                                       | 优点                                         | 代价与采用条件                                                            |
| ------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------- |
| 保留短事务，集合摊销附加计算               | 原子可见性简单，无新增领取和恢复成本         | 若实测附加工作很短且批量后没有锁竞争，保留；仍将规则收拢到所属能力        |
| 向量发布事务原子登记附加工作，后台分别完成 | 核心提交不再等待全部派生计算，失败可独立恢复 | 会增加任务、SQL和最终一致性；仅在核心延迟／锁等待下降且总成本可接受时采用 |

采用后台拆分时必须同时满足：

1. 向量READY与附加工作持久意图在同一事务提交，不能事务提交后靠内存EventEmitter“再发个事件”。唤醒通知只提示，丢失通知不丢工作。
2. 优先复用既有领域事实、任务种类和断点。确实缺协议时允许最小的领域扩展，但先更新北极星、能力归属、任务契约及门禁；不把每个模块变成独立消息系统。
3. 幂等键覆盖owner、mode、资产及媒体版本、向量记录／空间，以及所需快照或规则版本。幂等不只是忽略唯一键错误，重试必须校验结果是否仍适用。
4. 发布后被回收、永久删除、替换原件、切换空间、重建文件夹快照或变更推荐规则，旧附加任务不得写回失效结果。
5. 推荐重试不得复活用户已拒绝／已处理的建议。文件夹匹配仍按当前空间、可见性及快照发布协议执行，不承诺立即一致却显示已完成。
6. 暂停、时段、权限及分类沿共用任务规则；只用已有向量匹配不额外占GPU，必须推理的工作仍受EMBEDDING预算。依赖失败的重试不重跑已成功的原图向量。
7. 任务中心区分向量已完成和附加处理待完成，读取端不因延后处理暴露失效或私密资源。没有状态事实时不伪造进度。
8. 升级时同一资源版本只有一个附加处理发布者；避免旧内联代码和新任务同时生成建议。恢复、回滚及已有积压的迁移方案先用隔离数据库演练。

验收：模拟“向量提交后进程立刻退出、唤醒丢失、附加处理持续失败、已完成后重复投递”均不丢工作、不重复生效、不重跑模型。统计向量与附加任务总SQL、总事务、积压量和收敛耗时，而不是只展示主事务变短。若净代价不合算，明确选择保留短事务方案并删除试验性框架。

测试：向量发布、语义文件夹、标签推荐及审核、任务中心核心／SQL等价、真实数据库恢复、旧新版本切换回归。新增任务契约时同步Prisma／纯规则／DTO／展示／领取和发布门禁。

### W9 收拢危险确认的交互协议

对应E16。后台效率工作之外，统一焦点、描述关联、Escape层级和返回焦点；保留业务文案及异步状态。

1. 优先复现查重内层确认期间焦点能否逃到外层关闭按钮、提交中Escape是否关闭外层；确定关闭与取消任务的区别。
2. 公共底座提供标题／描述、内容和动作槽、取消、初始及返回焦点。业务组件拥有可恢复性说明、计数、错误、pending和何时关闭。
3. 原生window.confirm没有重复实现焦点；没有业务收益不强制把所有原生确认迁移。账号令牌、编辑器草稿与图片删除文案不能模板化成同一句。
4. 不增加普通回收的多余确认，不用确认框重构改变原产品流程。

验收：Tab／Shift+Tab、Escape、返回焦点、背景不可操作、描述可读、重复确认、请求失败和草稿保存失败通过真实浏览器验证；提交状态不因关闭对话框被误判为取消或回滚。

测试：`EagleDuplicates.test.tsx`、`SekerEaglePage.test.tsx`、`PhotoEditor.test.tsx`及新增交互底座契约测试。纯组件统一不作为SQL或后台吞吐收益申报。

## 7 实施依赖与变更拆分

按依赖推进，不给日期排期，也不要求一次提交所有模块。

1. W0先固定基线及现有成果，建立成本计数和关键故障用例。
2. W1关闭新增kind误入删除的风险，W2建立数据库批次预算。两项只收拢协议时保持运行成本不增加。
3. W3在现有元数据生命周期内优化批次，W4在向量领域内消除重复写并验证发布方式。它们不能共享一个跨进程事务框架。
4. W5只在W4的成本与结果语义清楚后决定是否拆分附加处理；W6在现有发送协议内独立验证标签映射和复制预算。
5. W7分离宿主时保持恢复协议，不能与新任务kind、新旧发布协议同时无边界切换。
6. W8按证据补充小范围提效；W9的删除安全缺陷可随对应功能修复，纯交互统一单独验收。
7. 每个变更单元完成自查、回归和成本对照后再叠加下一项。收尾合并验证两模式、真实数据库、网页及桌面，不用模块单测代替端到端。

拆分以可审查、可回退为准。不得以“同一轮架构优化”为由打包改变模型、数据库缓存、用户处理策略、媒体并发和产品行为。某一项收益未成立时撤回该项试验，实现其余已验证优化。

### 8.1 每项改动必须填写的记录

```text
场景与提交：
数据规模／模式／私密／实况／标签／派生对象：
机器／数据库／存储位置／冷暖缓存／模型／并发：
前后SQL（认证、准入、领取、发布、附加、清理、查询分列）：
前后显式事务／持锁时间／等待类型：
```

总成本包含新拆出的附加任务及新唤醒连接，不能只统计被优化的函数。物理清理可以晚于操作安排完成，两种完成时间必须分别展示。并行发生的空轮询按测量窗口记录，不能隐去成为“固定SQL常数”。

### 8.2 可确定的门禁与需实测的预算

| 项目         | 完成标准                                                                     |
| ------------ | ---------------------------------------------------------------------------- |
| 结构收拢W1   | 同一夹具SQL、S3、事务、HTTP零新增；未知kind不写资产                          |
| 分批W2       | 全量遍历及ordinal等价；真实语句参数不越界；没有用户数量上限                  |
| 元数据W3     | 32组2执行事务、零S3、最多512SQL；新的集合化提交必须比W0业务SQL更少           |

### 9.2 自动约束

- 使用现有 `scripts/architecture/library-sharing.mjs`、`library-runtime-boundaries.mjs` 和其反例测试，检查能力归属、非法依赖及第二套写入路径。
- 新操作kind必须登记处理协议；新领域处理器不能开元数据发布事务或直接结算操作状态。使用类型和AST边界检查，再以数据库测试证明事务语义。
- 数据库批次入口和语句预算登记配套边界回归；不能只数代码中的常量出现次数。
- API provider装配测试必须证明没有业务后台自动启动；独立宿主测试证明有可靠发现及排空。
- 增加每项领域成本断言，保护摊销阶数及SQL／事务／S3计数；不能只断言“调用了共用函数”。
- JS与SQL等待／策略规则保持真实数据库等价测试，任务kind及枚举双向契约不漏端。
- 业务错误和性能记录不输出对象键、原文件名、向量内容、token、凭据或用户私密元数据。

每个实现里程碑运行项目规定的lint、typecheck、单测和build；共享能力修改额外运行架构和共用契约。实际数据库测试前运行安全检查，只用 `sekereagle` 或 `sekereagle_test` 及loopback／compose服务目标。

## 10 风险和失败处理

| 风险                           | 预防和验证                                       | 出现时处理                                         |
| ------------------------------ | ------------------------------------------------ | -------------------------------------------------- |
| 以提效为由漏掉权限、版本或租约 | 每项发布故障注入，旧执行者迟到写回必须失败       | 回滚该发布改动，不降低守卫                         |
| 批量事务锁太久或单坏项拖全批   | 保持既有事务预算，记录锁等待；完整回滚后隔离冲突 | 降回已验证的内部执行工作量，不提高用户限制或时限   |
| 单槽向量等不到第二个结果       | 孤立单项、队尾、关闭和只一槽测试                 | 及时单项flush，必要时撤回合批设计                  |
| 附加任务丢失或无限重复         | 主结果和意图原子提交，幂等及持久发现             | 重放原领域任务；不补写虚假完成，不重推理已成功向量 |
| 推荐／文件夹规则变化复活旧结果 | 当前向量、快照、规则和人工决定守卫               | 旧工作作废或安全跳过，由现行规则重建               |
| 发送同名标签错误合并隐私       | 双模式同名异私密夹具及目标事务内事实             | 保留原冲突／改名规则，不强行按名字合并             |
| 复制预算嵌套死锁或放大         | 只叶子持许可，双模式／金字塔峰值测试             | 回退复制调度层，保持journal和在途排空              |
| API与新宿主重复或漏执行        | 交接与崩溃测试、数据库围栏                       | 排空后切回兼容宿主，持久意图保留                   |
| 缓存省I/O但泄露或吃满内存      | 权限版本键、字节预算及撤权清除                   | 禁用该缓存方案，保留原读取正确性                   |
| 减少刷新导致卡片或计数不实     | 真实分页、失败和终态交互回归                     | 修复范围化对账，不截页或要求用户手动刷新           |

问题发生时继续研究、修复和验证，不以“架构很复杂”搁置；但不能通过绕过门禁、提高预算、删数据或改变产品边界让测试表面通过。无法在既定范围成立的方案应撤回并记录替代决策。

## 11 发布和回退边界

本计划不安排生产操作。后续即使允许本地实现和提交，也要分别核对push、镜像发布、迁移、生产部署及真实资源操作的授权，遵守用户后续明确限制。

1. 发布前重读current-runtime，核对API、operations、业务worker、媒体节点和web实际版本及模型；不按历史安装文档猜运行状态。
2. 原则上不为结构整理新增schema。新增持久附加工作或任务契约若确需迁移，记录兼容窗口、索引／WAL成本、历史任务和回滚方法，不无差别回填全库。
3. 配套版本明确哪些可独立升级、哪些必须排空旧执行者并一起升级。不能只换web掩盖API／operations回执不兼容。
4. 涉及不可逆数据变更遵守现有备份和完整恢复要求；回退优先切回兼容执行版本，不用旧备份覆盖新用户数据。
5. 不调整用户暂停、夜间时段、节点策略或模型位置来制造提速。确需计算策略操作另按compute-fleet及专用工具，不能把源码重构当日常调度。
6. 实际获授权并执行Git push时，才按AGENTS和DeepSeek技能启动准确提交范围的独立后台审核；不在本地开发或文档交付自动触发，不等待审核作门禁，不把已启动称为通过。
7. 只有真正改变现用部署、处理开关、长期任务或模型位置，才同步current-runtime的日期和证据；不把本计划预期写成运行事实。

## 12 明确不做的方案

- 不推倒重建，不引入多租户、微服务拆分或新的消息中间件。
- 不引入万能 `delete(entityType, ids, options)`、通用parallelMap、通用线程池或多开关任务框架。
- 不将“模块独立”解释成各自创建队列、各自定时扫全库、各自实现租约与重试。
- 不把图片删除、标签删除、人物合并、快照替换和对象物理删除合成同一业务方法。
- 不把删除后立即失效改成等空闲再失效；不延后发布所需正确性校验到夜间。
- 不新增每日全表扫描孤儿向量作为默认解决方案；现有级联和outbox先保持，只有具体一致性缺陷证据才研究修复。
- 不把素材／照片隔离改成前端筛选，不让发送源进回收站，不重新下载／推理可复用向量。
- 不新增用户选择数量配额，不提高并发、像素上限、内存上限或事务超时来掩盖重复工作。
- 不为了接口数量加通用仓储或单纯转发层，不凭文件行数判断耦合，不为统一500／512声称速度提升。
- 不用减少前端请求的名义截第一页、丢游标、隐藏失败项或留下错误终态。
- 不承诺HDD顺序写入或固定提速倍率，不把本机合成测试称为生产p95。
