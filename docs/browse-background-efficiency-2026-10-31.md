# 日常使用卡顿与失败核查

日期：2026-10-31。对象：单 owner、约六万资源、NAS＋独立 Mac worker，默认网页／桌面。分支 `codex/browse-background-efficiency` 基于上一轮搜索与发送候选。仅本地代码、合成数据库、独立镜像验收；未 push、未部署、未清理真实图库、未改计算策略或节点凭据。用户提供的生产日志数字是问题线索，本轮没有把它们重新采样成当前生产结论。

## 核查结果

| 问题                         | 当前代码事实与处理                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 正常使用被 429               | 本地上一候选已移除 Nest 请求次数限流，网关也没有 `limit_req`；尚未部署，不能据此宣称线上 429 消失。本轮补网关反例门禁，并对最终镜像跑真实 HTTP 高频认证读取。认证、Origin、owner、请求体和媒体资源边界继续保留。                                                                                                                                        |
| 两模式进度反复轮询           | 原来运行中每模式 1.5 秒。现在变化后 2 秒，无变化 10 秒后降到 5 秒、30 秒后降到 10 秒；空闲保持原 60 秒。错误按 5／10／20／40／60 秒退避，关闭 React Query 的额外立即重试；隐藏页面不定时请求，离线沿用原暂停。两模式继续各自查询，保留当前模式才可读取私密操作的授权边界，没有增加跨模式读取旁路。                                                      |
| 队列每个任务读取时段配置     | 真实数据库复现：4000 项触发 4042 次设置表读取。本轮把全队列发现及唤醒的配置判断按 owner／模式在语句内物化一次；普通已知候选仍逐次用当前数据库条件复核。不是跨轮缓存暂停状态，也没有先截前 50 项再过滤，暂停任务不能挡住后面的可执行任务。                                                                                                               |
| 每轮扫全部 32.7 万历史任务   | 不能把累计统计等同当前每轮执行计划。本轮六万资源／三十万任务／2000 待办夹具中，旧版已经用状态位图索引读 2000 项，现有候选窗口也有摊销。没有为“消除全表扫描”强制错误索引或无限放大并发；实改是已复现的逐项配置开销。                                                                                                                                     |
| 已删除照片仍显示排队         | 任务中心主查询原本已排除回收和旧版本，但处理概览原来没排除，回归复现 1 项实际工作却报 3 项。本轮统一处理概览口径：当前 owner／模式／媒体版本，可见且未回收的资源，物理 PURGE 例外；五次任务计数／分组合成一次聚合。                                                                                                                                     |
| 删除后还有永远不会领取的任务 | 删除状态转移在原事务内将 PENDING／PROCESSING 的非 PURGE 媒体任务按原约定标记 `COMPLETED + ASSET_TRASHED`，增加 leaseVersion 作废旧发布权；不删除任务／事件，不覆盖成功历史或失败诊断。恢复仅重排当前版本的这些跳过项。迁移对既有回收资源作一次相同补齐，未应用生产。                                                                                    |
| 六万条退役 AI 失败记录       | 原迁移和当前任务中心／选择器已经排除退役生成，回归继续确认。保留诊断和历史，不通过删掉失败记录、伪造成功来改善数字。                                                                                                                                                                                                                                    |
| 发送慢、主搜索搬全库 ID      | 已由前两轮候选修复关键路径；本分支继承。发送仍独立执行，原 worker 激活复用向量；搜索仍完整精确分页，预览才 ANN。参见两份对应记录。                                                                                                                                                                                                                      |
| 远程媒体失败原因模糊         | 原代码把 401、400、500 等全部记成 `REMOTE_MEDIA_REQUEST_REJECTED`，413／415／422 也一律归为图片内容不符。现在保留安全的 HTTP 状态，受信节点返回的已知像素／解码／格式错误码经白名单保留；413 无已知原因时不谎报格式损坏。容量／暂不可用仍走原重试语义。没有日志和状态证据时，不能认定现有 23 张都由同一个节点配置错误导致，更不能自动改凭据或删除它们。 |
| 缩略图一图一请求、499 多     | 当前已是一次条件 GET，没有逐图重复 HEAD；响应会验证当前认证、owner、私密、媒体版本。取消滚出视口的请求本身不证明失败。客户端已有并发、字节缓存及失败退避；本轮不改成拼图、不放宽私密撤销，也不将所有 499 误算成服务错误。                                                                                                                               |
| 计数每次重算                 | 侧栏已有 60 秒查询新鲜期且无定时计数轮询；普通规则预览已有 250 ms 防抖、10 秒同条件缓存。没有为了掩盖 I/O 争用再加一份无法跨独立进程可靠失效的计数缓存，避免删除后缓存旧数字反过来覆盖即时投影。NAS 上 174 ms 样本仍需配套发布后的实际复测。                                                                                                            |
| 上传文件损坏／格式不符       | 不能仅凭数量认定系统错误。保留真实解码、字节、像素、格式校验；本轮没有降规格、放过损坏文件或静默转码来制造成功率。                                                                                                                                                                                                                                      |

## 批量删除不新增逐项开销

自查发现最初的逐行状态触发器会让 40 张批量删除触发 40 次任务更新，已经用 EXPLAIN 回归捕获并撤掉。最终采用语句级 transition table，一次资产批量 UPDATE 对应一次任务集合 UPDATE；40 项实际触发次数为 1。普通非删除更新只作当前语句转移集合的空变化检查，不扫描／更新任务表。未使用 API `setInterval`，未加新队列，未改变后台暂停／时段或原发布保护。

恢复继续使用共用 `mediaRequeueData`，按冻结资源 ID＋当前媒体版本限定；已成功工作复用，旧版本不会被恢复顺便重新排队。过期执行者不能因恢复得到新的发布权。迁移、触发器、任务事件及资产更新同事务，失败整体回滚。

## 实测与成本

安全检查通过的 loopback `sekereagle_test`，PostgreSQL 16／pgvector 0.8.6，六万合成资源、三十万媒体任务，其中 2000 待办。没有真实图像解码、NAS 磁盘或网络传输。旧／新选择 SQL 各六次交替执行，完整 50 项 ID 与顺序相同。

| 项目                       | 旧查询             | 候选               |
| -------------------------- | ------------------ | ------------------ |
| 配置表循环读取（末次计划） | 2000               | 2                  |
| 任务主表有效扫描行         | 2000，状态位图索引 | 2000，状态位图索引 |
| 缓冲页命中（末次计划）     | 12009              | 8015               |
| 六次排序后上中位耗时       | 15.66 ms           | 15.05 ms           |

减少约三分之一逻辑缓冲页访问，不声称暖缓存耗时快一个数量级；这也不能证明 NAS 物理磁盘读取减少相同字节数。50k 活跃候选摊销／依赖／新旧任务顺序、暂停变更和版本变化另由既有真实数据库测试验证。

端到端成本变化：

- 操作进度每次仍为一个模式请求与原状态查询，不写数据库、不读 S3、不刷新图库分页；两模式长期无变化时定时观察由约 4800 降到 720 次／小时，持续有新进度时会保持快速观察，不能把 85% 降幅推广到所有运行场景。用户主动操作和失效查询仍立即取数。
- 处理概览的任务统计从四条 COUNT＋一条分组降到一条集合聚合；加上心跳、颜色覆盖、设置和总量，常规概览为五条读取，无写事务／S3。没有将所有历史扫描成本说成零。
- 主队列发现与唤醒各仍为一条只读 SQL；配置表按当前语句的 owner／模式摊销，使用原依赖、模型、资源、时间、租约条件。候选发现和有界复核仍分开，配置变化不跨语句缓存。
- 一次批量删除在原资产事务中增加一次转移集合检查；确有删除时一次批量任务 UPDATE。每个真实任务状态变化沿用原持久事件记录，未删掉审计来省写入；没有 S3 读写或额外浏览器请求。恢复仍一次条件 UPDATE，限定当前版本。物理删除保持原独立进程。
- 远程失败只读一个有界错误正文，取消剩余流并保留安全原因；不新增重试队列，不把网络／节点故障归为原件损坏。已成功媒体计算字节路径不变。

## 新资源边界

`REMOTE_MEDIA_ERROR_MAX_BYTES` 默认 4096 字节，限制远程错误正文的内存聚合，正整数可调。到顶后取消错误正文，只记录 HTTP 状态，不把整个节点返回、路径或凭据带入任务错误。它限制诊断正文的资源占用，不限制照片数量、上传量或操作频率。非法值明确报配置错误；原媒体字节／像素／请求超时预算保持。

## 验收与发布边界

回归覆盖：真实双模式轮询计时、变化后恢复快速观察、错误退避；新调度快照、历史任务及当前依赖／暂停／版本复核；删除／恢复及旧发布租约；历史补齐回滚和成功／PURGE 保留；远程真实 HTTP 错误码和安全回退。轮询模块行／分支／函数覆盖率均为 100%。

最终根目录 lint、typecheck、unit test、build、format、架构门禁和共用契约通过；OpenAPI 契约无变化。完整真实数据库集成、历史升级和全表摘要一致的备份恢复通过；实际独立 worker 及远程媒体／向量协作验收通过。语句级删除与调度业务的专项 24 项真实数据库回归通过，调度快照模块行／分支／函数覆盖率均为 100%，并已进入默认集成门禁。阶段中捕获的逐行收尾、旧别名冲突及夹具排序干扰均已修正，在最终数据库和镜像上重新验证，没有把中间失败记录算成通过。

本地最终镜像高频 HTTP 验收包括 12 次成功登录、800 次认证读取、600 次媒体路由访问（不存在资源应返回 404，非真实媒体吞吐测试），没有 429；未认证 401、不可信 Origin 403、跨 owner 404、伪造 owner 输入 400 保持。并未用“去认证”来消除限流。

本轮新增第 71 项迁移，只在隔离数据库验证。最终代码仍是候选；线上现用镜像、68 项迁移、模型、业务 worker、计算策略及用户数据没有改变。发布前需要配套 API／独立 worker／网页及迁移，不能只更新网页后宣称所有后端问题已解决。用户要求暂不推送生产，故未 push／部署，也未启动仅 push 触发的独立审核。
