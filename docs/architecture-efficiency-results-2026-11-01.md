# 架构优化与效率提升：本地实施与验收

## 交付边界

依据[批准计划](architecture-efficiency-plan-2026-11-01.md)，在独立分支 `codex/architecture-efficiency` 实施。实施起点为 `89acbe96a1d9f39cd398a2dde3e239684b4f685b`；计划中的历史审计基线与实施起点不同，下面只把本次相同夹具的对照称为本次实测。没有 push、部署、生产迁移、现用模型／暂停／节点调整，也没有接触真实图库或其他系统。

本轮的成果是减少重复数据库工作，并封闭危险的默认分派、模型及建议发布边界；不能把拆分文件当成提速。所有数据库样本使用 Docker tmpfs 的隔离 PostgreSQL 16／pgvector、loopback `sekereagle_test`、随机合成 owner。SQL 由 Prisma query 事件计数，包含 BEGIN／COMMIT；事务按 BEGIN 计数。该口径不包含触发器内部SPI语句，触发器调用次数／耗时用回滚EXPLAIN另列，避免把三条客户端SQL误称数据库只干三次活。涉及对象的测试使用带计数的存储适配器，HANDOFF 不触碰对象。无真实 NAS 或模型吞吐测试，因此没有生产耗时、p95 或“HDD提速倍率”结论。

### 完整领域操作补测

500项普通删除两模式均为：准入11SQL／1事务＋16轮执行480SQL／32事务＝491SQL／33事务；恢复为准入10／1＋执行496／32＝506／33。该夹具另做16次进度读取48SQL、空闲发现3SQL，包含这两项后的领域总账分别为542与557SQL，事务仍33。两者S3零，不含HTTP与前端；本轮没有同夹具旧版500项实测，所以只申报成本，没有宣称这条原有批次写入又获得提速。

千组普通重复清理，两模式均按31轮32组＋末轮8组推进，领取／发布64事务；MATERIAL执行1120SQL，PHOTO1088SQL。另列列表审查12SQL／1事务、准入24／1、夹具每轮进度共96SQL、最后空闲发现3SQL，排空0SQL；含审查、准入和夹具进度的总量为MATERIAL1255／PHOTO1223SQL、66事务、零S3。进度采样是该夹具设定，不冒充浏览器实际轮询频率。该成本夹具是两图一组、无标签、无实况；带标签、实况、私密、冲突和回滚由业务回归另测。

清空六万PHOTO在原有5秒交互事务时限下，曾发生并行和完整串行集成超时；未改超时、并发或内存。相同隔离夹具单独复跑通过，不能据此覆盖完整集成失败。回滚EXPLAIN测得一次总6610ms，其中资源UPDATE约4051ms、任务INSERT约1151ms、逐行任务事件约852ms、唤醒约95ms；后续修复和最终结果另列。固定绑定和三条SQL不等于固定工作量；六万任务及其事件／索引仍会随N增长，不能承诺NAS满负荷五秒内完成或把“已安排”显示为物理空间已释放。

### 旧任务兼容回归

完整套件的任务中心回归发现：仅按当前媒体修订和`v1`冲突重排，会漏掉原实现同样重排的旧修订／旧processorVersion清理任务。已在同一集合语句补`requeued_legacy`，与当前身份的upsert集合严格互斥；范围仍为本owner／模式、本次marked资源及PENDING／FAILED／COMPLETED，PROCESSING完整保留。恢复预算、尝试、租约及时间字段与原重排协议一致，不回传ID、不增加事务或时限。

新两模式夹具验证当前、旧修订、旧处理器、仅旧任务时创建当前任务、正在处理、其他owner／模式、私密、未回收及晚于cutoff的范围，且各任务恰好一条转换事件。原任务中心重排回归重新通过；修复后完整串行重跑的六万项为3条SQL、最多11绑定、语句4657ms，仍一事务且没有ID列表；之前的8绑定是修复前检查点。整套退出结果另列。

### 数据库内部重复写入的收拢

六万项回归暴露任务事件触发器的逐行SPI开销后，新增迁移把INSERT／UPDATE事件分别改为transition-table集合INSERT：仍为每个实际状态／租约变化保留完整事件，不补历史、不把事件表当队列。心跳不记事件，回滚不泄漏事件或通知；INSERT唤醒按NAS／EMBEDDING各发一次，空批不发，UPDATE继续原列级触发协议，保留领取静默和显式无变化重排唤醒。

同口径回滚EXPLAIN记录：事件调用60000→1、852→389ms，INSERT唤醒60000→1、95→6ms。整语句6610→4373ms，但其中未改代码的资源UPDATE也4051→2961ms、shared reads25124→17527，证明缓存／堆物理状态不同；不能把全部耗时下降归因该迁移。普通客户端单文件六万项语句另测4549ms，保持原5秒时限。它不是生产p95，完整串行集成的六万PHOTO同路径已测4796ms并通过（不是生产p95），整套退出结果继续另列。应用层仍是3条SQL／1事务／最多11绑定，触发器内部节省另外记账。

### 规模切换下的事件执行计划

集合触发器的小批回归没有覆盖PL/pgSQL计划缓存：完整积压测试的一条五万任务UPDATE曾持续CPU执行超过121秒、没有锁等待。为停止该隔离测试的失控运行，主动取消了这条自建测试容器查询；该整套退出失败保留为中断记录，没有冒充自然业务断言失败或生产事故。

新增专用回归使用同一个pg.Client连接先执行六次单行转换，再执行五万行失败、重排及无变化心跳，并用auto_explain捕捉触发器内部真实计划。旧函数重用了小批Nested Loop，五万行触发仅测试会话的10秒失败保护（57014）；固定可信SQL改为EXECUTE重新规划后，同backend三种大批均为Merge Join，两张transition relation各50000行／扫描一次。初始事件50000、失败50003、重排50003，心跳前后总数相等，混合upsert、回滚及资源通知测试保持。

这不是拼接用户输入，也没有修改planner开关、work_mem、生产事务时限或资源并发。回归同时检查实际扫描规模和结果事实，测试超时仅防止CI再次陷入平方级工作，不作为NAS响应承诺。

## 明确保留的方案

- **保留即时逐结果向量提交**：单槽只有一个就绪结果。攒满批次会拖延队尾或需要新暂存协议；目前合并同一结果SQL已有确定收益，没有增加缓冲、定时发布器或第二份结果事实。
- **保留向量与派生结果的原子短事务**：同20项的乐观持久后处理实验为300 SQL／40事务，原子方案180／20，结果相同且积压均零。拆分即使省去生产发现、重试和展示开销仍多120 SQL／20次提交；不增加生产任务或表。实验表仅测试时创建，finally删除。
- **不新增读图缓存**：颜色使用THUMBNAIL，分析／推理可能各读PREVIEW，不能说它们总读同一对象。已确认可能重复GET，但尚无字节、解码和内存净收益证据；已有单任务Sharp复用、资源预算和SEND存量向量零GET路径，保留。
- **不新增增量计算框架**：语义文件夹已有queryVector与持久游标，新向量只匹配当前项；地图已有dirty/version快照与有界推进；统计是一条集合SQL。没有证据支持另加全局事件层、缓存表或重建机制。
- **保留PhotoEditor专属交互**：编辑器具有输入、草稿、编辑历史及水印Esc语义，不把它套入删除确认组件。原生confirm保持原业务行为，不以统一外观扩大范围。
- **保留回收、恢复、直接退休和物理删除的不同语义**：发送源项不进回收站；标签本体不跟图片关联一起删；数据库级联和outbox继续各负其责。
- **保留资源分层**：NAS、EMBEDDING、REMOTE_MEDIA的名额与内存预算不改；发送只收拢叶子复制许可，不引入通用线程池、parallelMap、Redis或另一套租约。

## 升级与回退约束

这是未发布的整套源码候选。operations配置透传既有上传发布时限（默认30000ms）及恢复开关，显式false仍关闭自动恢复，不改变S3独立连接预算。API与operations的后台宿主交接应一起升级，或先停止旧API发现并排空，再启动兼容operations；不能先停旧恢复又长期不启动新宿主。原上传会话、cleanup标记、journal和任务表都保留，重启依原事实恢复，不重放已移交源对象删除。新增 `20261101030000_media_transition_batches` 仅替换触发器实现，不新增任务事实表或补写历史；只在隔离测试库应用，生产尚未迁移。部署前仍须按既有备份、迁移及最终镜像启动要求验收。向量API／worker／共享规则及网页操作协议按同一候选构建验收；不靠只换网页掩盖服务端差异。
