# SekerEagle 网页与桌面前端架构检查

> 本文记录审查当时的状态；后续已修复项、仍保留的结构建议和验收限制见[修复记录](frontend-architecture-remediation-2026-10-30.md)，不能把本文原始发现当作当前缺陷清单。

检查日期：2026 年 10 月 30 日。范围为网页、Electron 桌面适配及其共享前端基础设施。结论：共享图库和业务隔离的方向合理，但异步任务、查询缓存、实体仓库之间缺少统一的生命周期与一致性契约，已经产生可复现的问题。应先修复这些契约，再拆分工作区职责。

这是检查报告，不代表业务代码已修复或生产已更新。审阅起点 HEAD 为 `bc012ff8cc3fbe3b3e13f34b6756acc44c82080c`，包含当时工作区已有的未提交修改；期间存在其他任务的并行编辑。源码引用指向本次读取位置。未访问现用图库、生产数据库或 SekerChat，未执行 push、部署或运行策略变更。

## 关键发现

严重程度：P1 应优先修复；P2 影响一致性、资源占用或操作可靠性；P3 为当前影响有限、应随契约整理修复的问题。

### F1 P1 上传队列没有绑定认证会话的有效期

位置：[useEagleUploadController](../apps/web/src/components/eagle/useEagleUploadController.ts#L23)、[浏览器认证客户端](../apps/web/src/lib/api-client.ts#L51)、[App 工作区装配](../apps/web/src/App.tsx#L299)。

队列捕获了模式 API 和查询键，但没有取消信号、会话代次或卸载后的停止领取守卫。App 按 owner／mode 重建 Provider；卸载只移除了上传进度界面，旧 Promise 和剩余 File 仍被队列闭包持有。API 的 token 参数实际被忽略，请求使用当前 Cookie。单次请求的 authEpoch 能拒绝跨会话返回，却不能拒绝旧队列在新会话开始后发出的下一条请求。

最小复现使用真实上传 hook、真实模式 Provider 和真实认证请求封装，仅模拟 HTTP：账号 A 排入三个文件，前两个创建上传会话的响应阻塞；卸载工作区，退出并登录 B，释放旧响应。前两个请求因认证代次变化失败，但队列继续为第三个文件发起请求，模拟服务观察到主体为 B，并完成上传链路。

这不是读取 A 的服务端资源越权，而是旧用户意图中的本机文件被新账号上传。普通切换模式也会丢失旧队列的可见进度；切回后新 hook 可建立另一组上传名额，使“共用两路”只在单个 hook 实例内成立。

修复应让现有工作区拥有可观测的上传运行对象，模式固定且返回后可重新订阅；认证主体或会话撤销时停止领取并取消在途请求。模式切换与会话撤销必须采用不同的生命周期动作。不能只加 mounted 判断来屏蔽 setState。

### F2 P2 查询回收不能释放其独占的规范化实体

位置：[工作区缓存](../apps/web/src/components/eagle/eagle-workspace-cache.ts#L82)、[实体仓库](../apps/web/src/components/eagle/eagle-asset-entity-store.ts#L34)。

Query 页面只保留 ID，实体写入独立 Map。移除查询时只尝试销毁整个工作区；只要工作区仍被页面持有，或另一条列表查询仍存在，就不会回收任何历史实体。实体仓库没有逐项删除或按页面引用回收能力。

复现：缓存普通列表和一次搜索列表，移除搜索查询后，它独占的实体仍留在 Map。持续打开图库并搜索不同集合时，查询 GC 不构成实体内存的上界。缩略图虽有 512 项／128 MiB 限制，这个限制不约束实体 Map。

应按当前保留页面及独立详情消费者计算实体引用，覆盖查询移除、页链截短、重新规范化和私密清理；或者让 Query 直接拥有实体数据，取消这份第二存储。不能只给当前显示列表截断，因为缓存页面仍依赖这些实体。

### F3 P2 实体合并缺少版本顺序守卫

位置：[upsertMany 与 mergeProcessingUpdates](../apps/web/src/components/eagle/eagle-asset-entity-store.ts#L34)、[列表读取](../apps/web/src/components/eagle/SekerEaglePage.tsx#L574)。

不同搜索／筛选查询可以并行读取同一资源，所有响应都无条件写入同一个实体 Map。React Query 按查询键管理请求，不能替独立实体仓库判断不同键之间的新旧。

复现：仓库先有 rowVersion／mediaRevision 为 2 的资源，再规范化一个版本 1 的旧列表响应，结果退回版本 1。处理状态合并同样无条件覆盖媒体版本、更新时间和派生内容。实际结果可能是旧名称、评分或预览覆盖新结果；服务端版本校验仍可拒绝陈旧写入，不能据此声称服务端数据被覆盖。

需要统一定义元数据版本、媒体版本及同版本处理事实的合并顺序，并对乱序列表、轮询与写回做交叉测试。仅比较一个时间字符串不足以替代这些语义。

### F4 P2 批量写入的提前失败与写后刷新脱节

位置：[并发工具](../apps/web/src/lib/async-pool.ts#L13)、[标签批量更新与删除](../apps/web/src/components/eagle/useEagleMutations.ts#L182)。

工具用 Promise.all 等待多个循环。一个循环抛错后，调用者立即收到失败，其他循环仍会完成当前写入并领取后续项。标签更新和删除只在整体 onSuccess 中刷新查询，没有为部分提交提供结算和刷新路径。

复现：第一项失败，第二项阻塞；整体 Promise 已拒绝后，释放第二项，第二、第三项仍成功执行。界面可能已恢复可操作状态，而后台仍在修改；成功项也可能继续显示旧缓存，重试缺少逐项依据。

应明确批量操作的失败语义，停止新领取并等待在途项结算，或返回完整逐项结果；无论整体是否成功，都要刷新已提交项并呈现可重试集合。不要求把多个独立 HTTP 写入伪装成原子事务。

### F5 P2 推荐确认后的刷新没有覆盖共享图库

位置：[推荐确认](../apps/web/src/components/eagle/EagleVectorWorkspace.tsx#L279)、[确认后的处理](../apps/web/src/components/eagle/EagleVectorWorkspace.tsx#L337)、[公共列表新鲜期](../apps/web/src/components/eagle/SekerEaglePage.tsx#L599)。

普通 ACCEPT 会改变人工标签关系，但该路径只重载向量工作区自己的本地数据、清理桌面媒体缓存；仅在 privacyChanged 时调用父级重置。它没有失效共享列表、详情和人工标签相关查询。

因此，在公共列表仍处于五分钟新鲜期内，确认普通建议后返回原图库，已缓存资源的标签及标签筛选成员可能继续保持确认前的结果。这个结论来自源码调用链；本次未做完整浏览器点击复现。

应将“标签关系已改变”交给共用写后刷新入口，由它覆盖共享列表、详情、标签计数和向量摘要；组件自己的 reload 只负责自己持有的视图。不要为了刷新而伪造一次隐私规则变化。

### F6 P3 评分写回与详情查询使用不同的键

位置：[评分成功回写](../apps/web/src/components/eagle/useEagleMutations.ts#L103)、[详情查询](../apps/web/src/components/eagle/SekerEaglePage.tsx#L788)。

评分成功写入 `assetDetail(id)`，详情实际读取的是该键追加 libraryView 后的查询；随后只失效 assets。复现运行真实 mutation hook 后，短键数据变成版本 2，详情查询仍是版本 1。

当前星级显示取自列表，后续提交版本也取列表与详情的最大值，所以不能把这一点描述成“点击星级必然显示错误”。它证明查询键工厂与消费者之间的契约已经漂移。应让工厂显式生成包含视图边界的详情键，并统一精确写回与前缀失效。

## 已有基础应保留

- App 按 owner／mode keyed 装配同一个工作区，公共查询键包含两者；素材与照片共用图库、筛选、媒体查看及通用操作。
- 已有独立浏览记忆、32 项滚动位置上限、缩略图 LRU、私密撤权清理与下载队列 epoch；这些是可继续扩展的基础。
- 浏览器使用 Cookie 和单飞刷新，单请求具备认证代次和超时守卫；F1 是队列生命周期未接入这套守卫。
- 大图、地图、统计、任务中心和编辑流水线已有按需加载及测试，不应把所有依赖重新放回首屏。
- Electron 已开启 contextIsolation、sandbox、webSecurity，拒绝新窗口，并在主进程验证 IPC 来源、身份及部署；本次没有证据支持删除这些边界或重写桌面壳。

## 建议修复顺序

1. 先处理 F1，把会话撤销接入队列与在途任务；验证真实 owner 切换、模式切换、卸载重建、失联恢复及重复拖入的总并发上限。
2. 整理缓存一致性，处理 F2、F3、F5、F6。统一查询键与写后刷新规则，明确实体的引用回收和版本合并契约；验证跨查询乱序、部分页面 GC、私密撤权和确认建议后返回图库。
3. 处理 F4，统一批量部分成功的反馈、停止领取、排空与刷新；对失败后的立即重试补行为验证。
4. 在上述契约稳定后拆分 D1 的职责，并收紧 D2、D4；保持唯一图库、Provider 与通用 API。桌面模式能力 D3 作为完整桥协议变更验收，不能只取消前端 PHOTO 判断。

每个修复里程碑运行 lint、typecheck、unit test、build；共享能力调整再运行 architecture:check 和共用契约测试。上传和 API 改动补安全测试。后续真实浏览器和打包桌面验收应覆盖用户可见操作，不把 jsdom 通过称为整机验收。没有必要在这一步引入新的全局状态库、复制照片图库或全量重写。
