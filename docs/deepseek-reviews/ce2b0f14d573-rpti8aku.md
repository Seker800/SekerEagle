**证据**

- `architecture.md:21` 写的是“自动刷新当前活跃查询……不要求手动加载”，但同一行仍标“本地候选”“尚未完成生产切换”，并链接到 `asset-operation-efficiency-2026-10-31.md`。

## 问题 2（中，待验证）：多页删除后的真实游标重取没有回归，预算文档的“后续游标按新结果重建”与现有实现不符

**文件与行号**

- `docs/deletion-auto-sync-2026-10-31.md:12,20`
- `docs/performance-budget.md:61`
- `apps/web/src/components/eagle/asset-operation-refresh.ts:20-38`
- `apps/web/src/components/eagle/asset-operation-refresh.test.ts:5-59`
- `apps/web/src/components/eagle/SekerEaglePage.test.tsx:685-707`
- `apps/web/src/components/eagle/SekerEaglePage.tsx:727-733`
- `apps/api/src/eagle/eagle.service.ts:318-336`

**触发条件**

已加载多页列表（P > 1）时删除一项，且被删除项恰好位于页边界／是下一页游标所指向的项，随后自动刷新重取全部已加载页。

**证据**

- 新文档第 12 行称“自动重取有当前 P 页至多 P 次列表读取的成本”，并让读者详见 `performance-budget.md`。
- `performance-budget.md:61` 进一步写“后续游标按新结果重建，避免删除造成分页缺口”。
- 实际实现 `asset-operation-refresh.ts` 只是调用 `client.invalidateQueries(..., { refetchType: 'active' }, { cancelRefetch: false })`，没有自定义分页重建逻辑；React Query 的无限查询重取会复用已有 `pageParams`。
- 12 页回归 `asset-operation-refresh.test.ts:5-59` 使用的 `pageParams` 是 `"0"` 到 `"11"` 的数字，不是真实编码游标；每页的 `deleted-i` 也不是该页的游标项。它验证的是“旧页保留 + 12 页都重取”，没有验证“删除页边界项后重取无重复／无缺口”。
- 滚动断言在 `SekerEaglePage.test.tsx:685-707`，是**单页**场景；12 页测试没有滚动断言。因此“12 页保留”和“滚动属性”是两个独立测试，并不是“多页删除后滚动仍正确”的组合验证。
- 生产验收第 19 行只用了每模式两张图，实际只有一页；没有覆盖多页删除。

**实际影响**

- `performance-budget.md` 中“避分页缺口”的保证目前没有实现或测试证据，属于**待验证陈述**。
- 服务端游标是键集游标（`eagle.service.ts:318-336`），旧游标在语法上仍有效；实际更可能出现页边界重复项而不是直接漏项。`SekerEaglePage.tsx:727-733` 用 `Map` 去重，能消掉重复卡片，但缺少对“删除边界项后所有已加载项仍完整”的回归。
- 如果确实出现重复／漏项，用户可见表现是列表数量或滚动位置异常；目前文档和测试不足以排除这一点。

**修复方向**

- 增加一个使用真实编码游标的回归：加载至少 2～3 页，删除某页最后一项（游标项），触发自动刷新，断言合并后的资源集合不重复、不遗漏，并保留滚动位置。
- 核对 React Query 重取是否真的需要“重建游标”。若实现仍是复用旧 `pageParams`，应修正 `performance-budget.md` 的措辞，或实现真正的游标重建。
- 在验收记录中把“12 页保留”明确写成“页面保留与重取次数”，不要让它被理解为“多页删除后的分页正确性已验证”。
