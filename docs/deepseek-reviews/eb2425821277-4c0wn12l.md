## 一、行为问题

### 1. 提前离开进度页后，图库不会随操作终态刷新（中）

- 位置：
  - `apps/android/app/src/main/kotlin/com/sekereagle/android/NativeTransferScreen.kt:70-85`：操作队列只在传输页可见时轮询；
  - `apps/android/app/src/main/kotlin/com/sekereagle/android/NativeGalleryViewModel.kt:852`：只在关闭传输页时 `refresh()`；
  - `NativeGalleryViewModel.kt:1101`、`:112-115`：发送成功后只把“另一个模式”标记 stale，当前模式未标记；
  - `NativeGalleryViewModel.kt:1208-1252`：只有回到前台才再次刷新。
- 触发条件：用户确认发送后，在进度变成 `2/2` 之前点“返回图库”，随后操作在后台完成；用户停留在图库浏览。
- 证据：客户端没有任何“操作进入终态”的回调。`transferRefreshPending` 只由上传/下载事件驱动（`NativeGalleryViewModel.kt:252-267`）；`AssetOperation` 只在发送和进度页读取路径中出现。终态完成时，客户端不会再次读取列表。
- 实际影响：
  - 服务器已把源项标记为不可恢复删除（`deletedAt/purgeAfter`，见 `apps/api/src/eagle/eagle-library-transfer.service.ts:463-503`），但客户端仍显示并允许点开源图库卡片；点开可能进入已失效资源的查看器/预览请求。
  - 另一个模式中已发布的目标副本也不会及时出现，用户可能误以为发送失败而再次选择发送（第二次入队通常会在源项消失后失败，形成一条无意义的失败记录）。
  - 服务端数据本身正确，不属于数据损坏或越权。
- 修复方向：在进度轮询观察到 `queued+running == 0` 的终态时，至少刷新当前模式；离开进度页时若操作仍未终态，不要求立即刷新源项（保持现有“延迟移除”），但应在下一次图库可见/前台恢复时对受影响的双模式做一次刷新。可复用现有 `invalidateInactiveLibrary()` 思路，把“发送已受理”与“发送已终态”分开处理。

### 2. 队列卡片未展示排队/进行中数量，也没有重试/取消入口；文档说法高于实现（低）

- 位置：
  - `NativeAssetOperations.kt:20-37`：`queued`、`running` 只参与 `pending` 布尔判断；
  - `NativeTransferScreen.kt:147-151`：只显示“已完成 X/Y”、pending 进度条和失败提示，没有排队数、进行中数，也没有操作按钮；
  - `docs/android-client.md:7`：写“传输列表显示成功、失败、取消和进行中数量”。
- 触发条件：任意 `queued>0` 或 `running>0` 的操作；或部分项失败、源项仍保留的情况。
- 证据：服务端已暴露 `POST /operations/:id/retry`、`/cancel`（`apps/api/src/eagle/eagle.controller.ts:103-119`），网页 `AssetOperationsPanel.tsx:108-127` 也提供“重试失败任务/停止排队”；安卓没有使用这些能力，只能提示“返回图库重新选择发送”。
- 实际影响：用户无法区分“排队中”和“正在处理”的数量；失败项只能重新发起新操作，不能复用原操作重试；文档中的“进行中数量”在 UI 中并不存在。
- 修复方向：在 `progress` 中展示 `running`/`queued` 数量，并按操作所属 `libraryMode` 接上 retry/cancel；若本轮确实不做重试/取消，至少修正文档措辞，避免把共用队列能力描述成已完整交付。

## 二、测试与边界问题

### 3. 设备测试存在异步断言时序风险，失败/取消路径无覆盖（低，待验证）

- 位置：`apps/android/app/src/androidTest/kotlin/com/sekereagle/android/NativeReviewTest.kt:179-180`。
- 触发条件：`await { !busy && transfersOpen }` 返回后立即断言“已完成 0/2 · 正在处理”。
- 证据：进度来自传输页的 `produceState` + `Dispatchers.IO` 轮询（`NativeTransferScreen.kt:70-85`），`await` 只等待 `busy/transfersOpen`，不等待第一次队列读取完成；Compose 的空闲判定通常不覆盖这次 IO 回调。该测试若在设备上稳定通过，可能依赖时序；我无法运行设备测试，标注为待验证的潜在 flaky，而不是确定失败。
- 实际影响：回归测试偶发失败，可能掩盖真正的回归。
- 修复方向：对“已完成 0/2 · 正在处理”也使用 `compose.waitUntil`；并补充失败/取消计数的卡片断言、队列读取失败时的错误文案断言。
- 另：当前测试未覆盖操作终态失败后“源项仍保留”的展示，也未覆盖 `publicOnly=true` 与跨 owner 操作是否被排除（当前测试只断言发送体不含 ownerId，见 `NativeReviewTest.kt:190`）。这些是测试缺口，不是已证实的生产缺陷。

### 4. 幂等键只存在内存中，进程被杀后会换新 operationId（低，设计限制，需主代理判断是否在验收范围）

- 位置：`NativeGalleryViewModel.kt:91`、`:1089-1100`、`:107`。
- 触发条件：POST 结果未确认（超时/断连），随后应用进程被杀，用户重新打开后对同一选择再次发送。
- 证据：`sendRequests` 是普通 `mutableMapOf`，只在成功或 `clearLibraries()` 时清理，没有持久化。服务端会按新 operationId 再建一条操作；不过 `EagleAssetOperationService.execute` 的源版本快照与 `EagleLibraryTransferService` 的发布事务会阻止对同一源版本产生第二份目标副本（`eagle-asset-operations.service.ts:567-586`，`eagle-library-transfer.service.ts:286-305`、`:463-477`）。所以主要影响是可能多出一条失败/无意义的队列记录，而不是重复复制目标。
- 实际影响：文档“未确认提交的重试复用操作编号”只在同一进程会话内成立；跨进程重启不成立。
- 修复方向：若该语义需要跨重启，持久化待确认的 operationId（按 scope/mode/选择集），或在文档中明确“仅进程内幂等”。

## 三、已核实通过的项

- 作用域隔离：安卓只按当前模式调用 `/api/photos/operations` 或 `/api/eagle/operations`（`NativeAssetOperations.kt:45-52`、`:55-77`），未发送 ownerId；服务端从认证主体推导 owner、按路由固定 `LIBRARY_MODE`，跨 owner/模式统一 404（`eagle-asset-operations.service.ts:154-166`、`eagle.controller.ts:83-120`）。
- 源项延迟移除：客户端在受理后只清选择并打开进度页（`NativeGalleryViewModel.kt:1097-1109`），不在本地删除源项；服务端在目标发布成功的同一事务里标记 `transferredAt/deletedAt/purgeAfter`，不进入可恢复回收站（`eagle-library-transfer.service.ts:463-503`）。
- 幂等：同选择重试复用同一 operationId（`NativeGalleryViewModel.kt:1089-1090`，测试 `NativeReviewTest.kt:207-227`）；服务端按 `owner+libraryMode` 检查已存在操作的 kind 与冻结的 assetIds，冲突返回 409（`eagle-asset-operations.service.ts:179-196`）。
- 队列展示：`NativeAssetOperations.list()` 同时读取两个模式并映射 `total/completed/failed/cancelled/queued/running`，传输页有进行中指示条和失败提示；最小展示成立。
- 网页生产代码未改：`apps/web` 仅新增 `SekerEaglePage.test.tsx` 用例，验证语义智能文件夹双选发送走 `enqueue` 而非旧 `sendEagleAssets`。
- 版本与文档：`build.gradle` 的 `versionCode 30 / 0.9.13` 与 `docs/android-client.md`、`docs/current-runtime.md` 一致。
