需要主代理关注的是**测试证据强度**和**一个退休窗口时序边界**，不是已证实的功能回归：

### 1. 中（P2）：运行中的内部取消路径没有任何测试真正执行到 `cancelRun(false)`

**文件与行号**

- `apps/android/app/src/main/java/com/sekereagle/android/BackupService.java:54-71`（`cancel()` / `cancelRun(false)`）
- `apps/android/app/src/main/java/com/sekereagle/android/BackupScreen.java:105,110,134,451,490`（改为 `cancelBackup()` 的五个内部停止入口）
- `apps/android/app/src/main/java/com/sekereagle/android/MainActivity.java:493-495`
- `apps/android/app/src/androidTest/java/com/sekereagle/android/MobileBackupTest.java:1147-1154`（新增 `internalStopDoesNotBecomeADurableUserPause`）

**触发条件与证据**

- 新测试只调用 `activity.enable(false)`，当前没有 `BackupService` 实例。`BackupService.cancel()` 在 `service == null` 时直接返回，`cancelRun(false)` 从未执行。
- 该测试仍能捕获旧实现的一个真实问题：旧 `enable(false)` 走 `pause()`，`pause()` 在检查 `current` 之前就无条件写 `userPaused=true`；因此第一段 `assertFalse` 对旧代码会失败。这一点是有效的。
- 但它没有覆盖本次改动最重要的场景：**备份正在运行**时修改目录/模式/全部相册，`BackupService.cancel()` 命中 `current`，执行新分支 `cancelRun(false)`。该分支负责不写 `userPaused`、清 `pendingRestart`、状态改为“备份已停止”。全套 androidTest 中没有一处是在 `BackupService.isRunning(scope)` 为真时调用 `activity.cancelBackup()` 或通过 UI 修改规则。

**实际影响**

新分支的正确性目前只靠代码阅读；若未来有人把 `cancelRun(false)` 改回写 `userPaused`、或误删 `pendingRestart = null`，现有设备回归不会发现。发布文档第 17 行“安卓内部取消……四项设备回归”的证据覆盖不完整。

**修复方向**

补一条真实运行中的内部取消回归：启动 run 并等待 `isRunning`，调用 `activity.cancelBackup()`（或真实修改规则/allMedia），断言 `userPaused` 仍为原值、状态为“备份已停止”、run 最终退休；再补一个 `userPaused=true` 时内部取消仍保留暂停的变体。

### 2. 低（P3）：`immediatePauseAndResumeRetiresTheLatestServiceStart` 的完成等待可能被历史 `lastFinished` 提前满足

**文件与行号**

- `MobileBackupTest.java:1127-1130`：`waitUntil(() -> !settings.value(scope, "lastFinished", "").isEmpty(), ...)`
- `MobileBackupTest.java:34-105`：`setUp` 没有清空 `lastFinished`
- 对照 `MobileBackupTest.java:220-233`：`runScan` 正确保存了 `previous` 并等待值变化

**触发条件与证据**

同一 suite 的 scope 固定（由 origin/owner/deployment 推导），`setUp` 只 `journal.forget(scope)`，未清 `lastFinished/status/counts`。只要前面任一测试跑过 `runScan()`，新测试的第一个等待就会立即通过，无法证明“恢复后的 run 完成”。后续虽然等待 `current == null`，但它只能证明某个 run 启动并退休，不能证明恢复的 run 成功上传；`exists(created.get(...))` 也可能由暂停前的第一次 run 满足（32×32 图片在暂停前可能已上传）。

**实际影响**

该测试可以“通过”而恢复的 run 实际失败（例如上传失败但正常退休），削弱了“快速暂停／连续恢复”的 RED/GREEN 证据。不是产品缺陷，但会让发布证据偏乐观。

**修复方向**

像 `runScan` 一样保存 `previous` 并等待 `lastFinished` 真正变化，或在 `setUp` 中显式清空 `lastFinished`；最好再断言恢复后 run 的完成状态或对唯一图片的存在性由恢复 run 产生。

### 3. 低（P3）：退休窗口会静默丢弃“允许的启动”；现有测试仍以 `running` 作为完成条件

**文件与行号**

- `BackupService.java:122-125`：`if (working.get()) { if (cancelled) pendingRestart = ...; return; }`
- `BackupService.java:248-267`：`settings.setFlag("running", false)` 在 worker 线程先执行，`working.set(false)` 延后到主线程 handoff
- `MobileBackupTest.java:228-233`：`runScan` 只等待 `!settings.flag("running")`

**触发条件与证据**

`finally` 先写 `running=false`，随后才 post handoff；在这段窗口内如果收到一次启动：

- `cancelled == true`：进入 `pendingRestart`，恢复路径正确；
- `cancelled == false`（正常完成的退休）：`onStartCommand` 直接 `return`，该启动被静默丢弃，随后 handoff 会 `stopSelfResult` 停服务。

该窗口很窄，且手动“立即备份/继续”在 UI 上被 `isRunning` 禁用，所以生产影响主要限于自动备份（例如 `onForeground` 触发的自动启动被丢弃后 `autoPending` 已被消费，需等下一次前台）和测试时序。`runScan` 以 `running=false` 作为“完成”信号，而新实现中 `running=false` 不再等价于 `working=false`，连续调用 `runScan()` 存在极窄的竞态窗口导致启动被丢弃、测试等待超时。此项未在设备上复现，属静态时序分析，建议作为待验证项。

**实际影响**

之前“旧完成回调停掉新 run”的严重竞态被正确修掉了；代价是正常完成退休期间的非取消启动不再被处理。生产影响低，但测试稳定性与自动备份的极端时序值得确认。

**修复方向**

在退休期间也把允许的启动放入待处理（或引入 retired/retiring 状态区分“正在跑”和“正在收尾”），由 handoff 统一启动；测试侧把 `runScan` 的完成条件改为等待 `!BackupService.isRunning(scope)` 或 `current == null`，避免把 `running` 当唯一完成信号。
