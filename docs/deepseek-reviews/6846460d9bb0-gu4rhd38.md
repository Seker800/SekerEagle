## 问题清单

### 1. [中] 生产 HTTPS 上传链路没有被本次的自动化守卫覆盖，“单一配置来源”只在初始暂存包内成立

**文件与行号**
- `scripts/deploy-nas.mjs:46-49`（把 api/worker/migrate 的 `S3_PUBLIC_ENDPOINT` 强制写回 `canonicalOrigin`，即 `http://localhost:8181`）
- `scripts/deploy-nas.mjs:110-115`（`prepareNasPackage` 从上述 compose 值取 `signedUploadEndpoint`）
- `scripts/deploy-nas.test.mjs:87-104`（新增测试只直接调用 `createNasGateway` 传入合成地址）
- `docs/nas-staging.md:57`（现用 HTTPS 安装使用独立的 `https.yml` 与 `nginx.https.conf`，不改初始包生成器）
- `docs/photo-editor-save-2026-11-01.md:7`（“打包器从同一API环境读取签名地址，避免两个配置分别写死”）

**触发条件**
下次维护/回退时，按初始包生成器重新生成 `nginx.conf`（Host 为 `localhost:8181`），而运行中的 API 通过 `https.yml` 使用公开 HTTPS 签名地址；或有人只更新 `https.yml` 的 `S3_PUBLIC_ENDPOINT` 而忘了同步 `nginx.https.conf` 的上传块 Host。

**证据**
`createNasStagingCompose` 无条件把 API 的 `S3_PUBLIC_ENDPOINT` 覆盖为 `canonicalOrigin`，因此 `prepareNasPackage` 读取到的实际上永远是 `http://localhost:8181`；仓库内不存在任何代码路径能渲染出生产正在使用的 `yuntai.design:8181` 这个 Host。新增测试仅覆盖 `createNasGateway(source, { signedUploadEndpoint })` 这一纯函数，没有任何测试断言 `prepareNasPackage` 写出的 `nginx.conf` 与生效的 API 配置一致，也没有测试覆盖 `https.yml`/`nginx.https.conf` 这对生产覆盖文件（它们不在仓库内）。

**实际影响**
当前生产已手工改好并可回退，所以不是现存功能故障；但“两个独立维护的配置漂移”正是本次故障根因，而新增 GREEN 测试在漂移复发时仍会全部通过。文档已提醒需保留一致 Host，但没有可执行的守卫。

**修复方向**
建议把暂存 compose 的签名地址做成可注入参数，补一条 `prepareNasPackage` 级测试（配置公开 HTTPS 地址时，生成 nginx 的上传 Host 必须等于该 host）；若生产覆盖文件继续放在 NAS 维护目录，则增加一个部署前一致性检查（比对生效的 `S3_PUBLIC_ENDPOINT` host 与 `nginx.https.conf` 上传块 Host），并在运行手册中写明这是强制检查项。

### 2. [低] 签名地址缺失时静默回落默认值；非法字符串则抛出未包装的 `TypeError`

**文件与行号**
- `scripts/deploy-nas.mjs:73`（`signedUploadEndpoint = canonicalOrigin` 默认）
- `scripts/deploy-nas.mjs:80-89`（先 `new URL(...)`，再自定义校验）
- `scripts/deploy-nas.mjs:112-114`（把可能是 `undefined` 的 compose 值直接传入）
- `scripts/deploy-nas.test.mjs:96-103`（只覆盖 5 种可解析但违反规则的输入）

**触发条件**
- compose 中 `S3_PUBLIC_ENDPOINT` 键缺失/改名时，传参为 `undefined`，解构默认值生效，静默生成 `Host localhost:8181`。
- 传入不可解析的值（如 `not-a-url`、端口越界、未插值的 `${...}`）时，`new URL` 在自定义校验之前抛出 `TypeError: Invalid URL`，不是约定的 `Invalid signed upload endpoint`。

**证据**
`new URL` 调用位于 `try` 之外且没有包装；测试仅用 `assert.throws(..., /upload endpoint/u)` 校验五种可解析输入。

**实际影响**
不会造成安全放宽（异常仍会中断打包），但会给出误导性的失败形态，或让缺失配置静默落到 loopback Host，属于排查成本与可维护性问题。

**修复方向**
用 try/catch 包装 `new URL` 并统一抛出 `Invalid signed upload endpoint`；`prepareNasPackage` 读取到空值时显式报错，而不是依赖默认值回落。

### 3. [低] 编辑器现在会把浏览器原生网络错误原文直接展示给用户

**文件与行号**
- `apps/web/src/components/media/photo-editor/PhotoEditor.tsx:437,478,489-493`
- `apps/web/src/lib/eagle-api.ts:746-754`（分片 PUT 使用裸 `fetch`，网络层失败抛出浏览器 `TypeError`）

**触发条件**
上传分片 PUT 因离线、DNS、TLS 等网络层原因失败（非 HTTP 状态失败）。

**证据**
`fetch` 网络失败会 reject `TypeError`（Chrome: `Failed to fetch`，Safari: `Load failed`，Firefox: `NetworkError when attempting to fetch resource.`）。该错误不是 `ApiError`，但 `savingToAlbum` 为 true 且 `cause instanceof Error`，因此原文进入 `setError`，替代了原来的“照片保存失败，请重试。”。HTTP 403 的本地化文案（`上传分片失败（403）`）不受影响。

**实际影响**
恰好在本修复关注的“网络不稳定”场景下，用户看到的是未本地化、不可操作的浏览器内部文案；不涉及数据或权限。另外 `onSave` 内部若出现编程性 `TypeError`，也会把内部细节暴露到界面。

**修复方向**
在 `uploadEagleAsset` 内为 PUT 的 `fetch` 失败包装成明确文案（如“上传分片失败：网络中断，请重试”），或在编辑器中对非 `ApiError` 的 `TypeError` 回退到通用提示，同时保留 HTTP 状态类错误的透出。这属于取舍，若产品明确要求“任何上传错误原文透出”也可维持现状，但建议至少覆盖网络层错误。
