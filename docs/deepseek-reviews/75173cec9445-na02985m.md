## 1. 中：能力登记未覆盖全部共享持久模型，门禁也不检查完整性

**位置**
- `apps/api/src/eagle/library-capabilities.ts:37-136`
- `apps/api/src/eagle/library-assembly.test.ts:50-51`
- `scripts/architecture/library-runtime-boundaries.mjs:122-126`

**触发条件**
- 新增一个共享 Prisma 模型（例如新的 outbox、索引或状态表），但不在 `EAGLE_LIBRARY_CAPABILITIES.tables` 中登记；运行 `npm run architecture:check` 和 API 测试。
- 或直接检查现有登记：schema 有 74 个 model，登记中只有 30 个。

**证据**
- `apps/api/prisma/schema.prisma` 共 74 个 `model`；`library-capabilities.ts` 的 `tables` 合计约 30 个。
- 大量明确的共享模型未登记，例如 `EagleSmartFolder`、`EagleAssetColorAnalysis`、`EagleAssetColorSwatch`、`EagleMediaJobEvent`、`EagleProcessingWorkerHeartbeat`、`EagleObjectDeletion`、`EagleAssetEditRecipe`、`EagleAssetTransferFacts`、`EagleSmartFolderSemanticSnapshot`、`EagleSmartFolderSemanticMatch`，以及向量索引相关表。
- 门禁只反向校验“已登记表是否存在”：`for (const table of tableOwners.keys())` 检查 schema 中是否有 `model X {`，从不遍历 schema 的 model 并要求登记。
- `library-assembly.test.ts:51` 断言消息是 “each durable table has one capability owner”，但它只检查已登记表的去重，无法证明未登记表有 owner。

**实际影响**
- “按能力登记持久模型”只完成了一部分；未来新增共享表可以绕过能力归属直接落地，登记表会持续漂移。
- 文档和测试给出“每张持久表都有唯一 owner”的强信号，但实际门禁不成立；这会误导后续维护者。

**修复方向**
- 在门禁中枚举 `schema.prisma` 的全部 `model`，要求每个 model 要么登记到一个 capability，要么出现在显式的例外清单（如认证、纯摄影表），并对未登记 model 报错。
- 或者缩小声明范围，明确登记只覆盖“共享库能力拥有的表”，同时把测试消息和架构文档改成一致口径。
- 登记当前明显属于共享能力的模型，尤其是 `EagleObjectDeletion`、`EagleAssetEditRecipe`、`EagleAssetTransferFacts`、`EagleSmartFolder*`、`EagleAssetColor*`、`EagleMediaJobEvent`、`EagleProcessingWorkerHeartbeat`。

## 2. 中：运行时边界门禁对“所有共享包”的覆盖不完整

**位置**
- `scripts/architecture/library-runtime-boundaries.mjs:210-213`
- `docs/library-sharing-gate.md:20`

**触发条件**
- 在 `packages/eagle-filter-core/src/` 中新增 `import { readFile } from 'node:fs/promises'`，或 `import { PrismaClient } from '@prisma/client'`；运行 `npm run architecture:check`。

**证据**
- 门禁只把 `packages/library-core/src/` 和 `packages/photo-render-core/src/`（除 `server-render.ts`）定义为 `pure`；`browser` 只覆盖 `apps/web/src/`。
- `packages/eagle-filter-core` 是浏览器实际使用的运行时包：
  - `apps/web/src/components/eagle/EagleQuickFilterBar.tsx:2` 导入 `getEagleFilterFields`；
  - `apps/web/src/components/eagle/SekerEaglePage.tsx:70` 导入 `readEagleSemanticIntent, toEagleFilterQuery`。
- 因此向 `eagle-filter-core` 加入 Node／Prisma 依赖时，当前门禁会静默通过；只有 Vite 构建或运行时才会暴露。
- 同类问题也适用于 `packages/vector-core`、`packages/contracts` 等被声明为纯共享的包（是否属于浏览器共享需按实际导入面确认）。

**实际影响**
- 门禁宣称覆盖“所有共享包／纯规则包”，但实际只保护了两个包；浏览器端共享规则包被污染时不能在 `architecture:check` 阶段失败。
- 这与“架构门禁扩到 worker 和所有共享包”的需求只完成了一半。

**修复方向**
- 明确一份“浏览器／纯规则包”白名单，至少包含 `eagle-filter-core`；对白名单包应用与 `library-core` 相同的 Node／Prisma／S3／服务端入口禁令。
- 增加反例测试：在 `packages/eagle-filter-core/src/new-rule.ts` 中加 `node:fs` 导入，门禁必须报 `runtime-boundary`。
- 如果 `vector-core` / `contracts` 也属于纯共享包，一并纳入；如果属于服务端包，在文档中明确说明。

## 3. 中（待验证）：`EagleService.imageSearch` 改成显式联合类型可能改变 DI 元数据

**位置**
- `apps/api/src/eagle/eagle.service.ts:90`
- 相关使用：`apps/api/src/eagle/eagle.service.ts:232`
- 现有可选注入写法参考：`apps/api/src/eagle/eagle.controller.ts:90-91`、`apps/api/src/photos/photo-agent.service.ts:88`

**触发条件**
- Nest 从 `EagleModule` / `PhotoLibraryModule` 解析 `EagleService` 时，读取 TypeScript 的 `design:paramtypes` 元数据。

**证据**
- 改动把：
  ```ts
  @Optional() private readonly imageSearch?: EagleImageSearchService
  ```
  改成了：
  ```ts
  @Optional() private readonly imageSearch: EagleImageSearchService | undefined
  ```
- 仓库中其他可选注入都使用 `?:` 形式；这一处是唯一显式 `T | undefined` 的构造函数注入参数。
- 在 `emitDecoratorMetadata` 下，显式联合类型是否序列化为 `Object` 取决于编译器实现；本环境未运行 `tsc`，无法直接确认。
- 如果元数据变成 `Object`，`@Optional()` 会让 Nest 注入 `undefined`，而不是 `EagleImageSearchService`。此时：
  - `listAssets` 在 `:232` 的 `if (filters.search && this.imageSearch)` 为假；
  - 搜索退化为名称／人工标签匹配，语义／图片搜索静默失效。
- 新增的 `library-assembly.test.ts` 只解析 `EagleAiTagService`，不解析真实的 `EagleService`，因此不会覆盖这个点。

**实际影响**
- 如果元数据确为 `Object`：两个库的搜索功能在 API 运行时静默降级，不报错、不启动失败，现有单测和人工构造的集成测试也未必发现。
- 如果编译器对联合类型取首类型，则无影响；这是待验证项，不是已确认缺陷。

**修复方向**
- 优先回退为 `imageSearch?: EagleImageSearchService`，保持仓库既有可选注入写法。
- 或保留显式 `| undefined`，但加 `@Inject(EagleImageSearchService)`，避免依赖元数据推断。
- 增加一个真实模块装配测试：从 `EagleModule` 解析 `EagleService`，断言 `imageSearch` 已注入；或直接检查编译产物中的 `design:paramtypes`。

## 4. 低：查询键识别器没有在所有消费点集中

- `apps/web/src/components/eagle/eagle-workspace-cache.ts:204,224-228`

**触发条件**

- `EagleTaskCenter` 仍然使用：
  ```ts
  query.queryKey[0] === 'eagle' &&
  query.queryKey[1] === ownerId &&
  query.queryKey[3] === 'operations'
  ```
  没有使用 `isEagleOperationKey`，也没有检查 mode。
- `eagle-workspace-cache` 仍然使用：
  ```ts
  queryKey.length === this.#keys.assets.length + 2
  ...
  key[3] === 'assets' && key.length === 6
  ```
  没有使用 `isEagleAssetListKey`。
- 需求要求“列表、库计数、操作回执键工厂和识别器集中”，目前识别器只在回执刷新中集中，两个消费点仍是位置猜测。

**实际影响**
- 目前 tuple 形状未变，所以没有即时回归。
- 但未来改键形状时，任务中心的“刷新任务中心后失效操作回执”会静默失效；工作区缓存的 `#collect` 可能误判列表已不存在，提前清空实体和缩略图，造成可见的数据/滚动状态问题。
- 这属于“识别器集中”需求只完成一部分，不是当前功能错误。

**修复方向**
- `EagleTaskCenter` 用 `isEagleOperationKey` 对两个 mode 做判断，或新增不要求 mode 的 `isEagleOperationPrefixKey`。
- `eagle-workspace-cache` 用 `isEagleAssetListKey(queryKey, ownerId, mode)` 判断列表；`queryAssetReferences` 同样复用。
- 给这两个消费点补单元测试，避免后续键形状变化静默失效。

