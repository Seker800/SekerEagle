## 1. 取消保护按 `isPrivate` 维度保存，隐私可见性变化后仍可能自动重扫

**严重程度：低（可导致一次意外全库扫描，无数据错误）**

**文件与行号**
- `apps/api/src/eagle/eagle-duplicates.service.ts:299-311`（`operation: { isPrivate: principal.canViewPrivate }`）
- `apps/api/src/eagle/eagle-duplicates.service.ts:339`（`admit(..., principal.canViewPrivate, ...)`）
- `apps/api/src/eagle/eagle-duplicate-read.ts:67-73`（`o."isPrivate"=${includePrivate}`）
- `apps/web/src/components/eagle/EagleDuplicates.tsx:200-212`（自动触发按当前 `data` / `includePrivate` 判断）

**触发条件**
1. 私密可见性开启（`includePrivate=true`、`canViewPrivate=true`），首次打开查重，前端自动发起 `onlyIfUnattempted=true`，服务端创建 `isPrivate=true` 的扫描（无论页面是否只显示公开项）。
2. 用户取消该扫描，`build` 项保留版本，`originalCheckAttempted` 对 `isPrivate=true` 为 true。
3. 私密可见性过期或关闭（`includePrivate=false`、`canViewPrivate=false`）。
4. 重新打开查重：读取侧按 `o."isPrivate"=false` 查询不到刚才的尝试，若公开范围此前没有完成的扫描，则 `originalCheckAttempted=false`、`originalCheckCompleted=false` 且 `coverage.total>0`；`stoppedScan` 也因操作列表按公开范围过滤（`listOperations` 传 `canViewPrivate=false`）看不到那个私密扫描而保持 false；自动 effect 会再次发送 `onlyIfUnattempted=true`，服务端按 `isPrivate=false` 也查不到尝试，于是**自动创建新扫描**。

**实际影响**
用户明确取消检查后，仅仅因为隐私可见性窗口变化/关闭，重新打开页面会再次自动开始检查。若之前取消的扫描没有留下可复用指纹，这可能是接近全库的重新扫描，而不是简单的投影刷新。它不违反 owner/mode/私密隔离，也不丢数据，但与本次“取消后重新打开不得自动重启”的目标在隐私范围切换这一维度上不一致。该行为与本次改动前一致（属既有缺口），本次的版本化尝试并未覆盖它。

**修复方向**
- 若“取消后不自动重启”应跨隐私范围生效：自动路径的尝试判断应覆盖同一 owner+mode 下当前算法版本的任意尝试（至少对已取消/已尝试的版本），或在服务端 `onlyIfUnattempted` 中对“更宽范围已有尝试”返回 `alreadyAttempted`。
- 若设计上就是“每个私密范围独立自动重建”：建议在文档/文案中明确，避免用户把隐私切换后的自动扫描理解为取消无效。

**验证**
代码路径可证实；真实环境未执行。需要产品确认“取消”是否应跨 `isPrivate` 维度。

## 2. 前端 `stoppedScan` 未按尝试版本限定，可能压掉算法版本升级后的自动一次重建

**严重程度：低（边界场景，可能长期停留在“正在核验”文案且无实际任务）**

**文件与行号**
- `apps/web/src/components/eagle/EagleDuplicates.tsx:146-148`（`stoppedScan` 只看最近 30 个操作里是否有 `cancelled>0` 的 `DUPLICATE_SCAN`）
- `apps/web/src/components/eagle/EagleDuplicates.tsx:200-223`（自动 effect 要求 `!stoppedScan`）
- `apps/web/src/components/eagle/EagleDuplicates.tsx:440-445`（`originalCheckAttempted=false` 时展示“正在核验原图”）

**触发条件**
1. 在旧分组版本下取消过一次扫描，该操作仍在操作列表最近 30 条内。
2. 随后部署新的 `DUPLICATE_GROUPING_VERSION`（或出现 `outdatedGroups>0` 的等价情况）。
3. 重新打开查重：当前版本没有尝试，`originalCheckAttempted=false`；服务端本会允许自动重建，但前端 `stoppedScan` 为 true，自动 effect 不发送请求。

**实际影响**
旧的近似分组继续处于停用状态，本应“打开过期结果时自动入队一次版本重建”的行为被跳过；同时因为 `originalCheckAttempted` 仍为 false，界面会显示“旧版近似结果已停用，正在核验原图”，但实际没有任何扫描在跑，用户不一定知道需要手动点“检查新内容”。服务端 `onlyIfUnattempted` 已经是按版本判断的，前端这个未按版本限定的补充判断反而过度拦截。

**修复方向**
- 让 `stoppedScan` 仅在“当前版本已经存在尝试、但结果元数据尚未追上”时生效（例如与 `data.algorithmVersion` 或更精确的尝试信息结合），或直接去掉这层前端兜底，依赖服务端 `onlyIfUnattempted` 的版本化保护。
- 至少让 `outdatedGroups` 且 `originalCheckAttempted=false` 时不要展示“正在核验原图”，改成明确的“点击检查新内容”。
