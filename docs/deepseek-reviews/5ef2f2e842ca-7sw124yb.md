## 问题清单

### 1. [中] 安卓：内部“停止”被持久化成 `userPaused`，会静默关闭“打开时自动备份”

- 位置与证据
  - `BackupService.pause()` 无条件写 `userPaused=true`（`apps/android/.../BackupService.java:44-52`），`pauseRun()` 再写一次（`:54-62`）。
  - `MainActivity.pause()` 直接调用它（`MainActivity.java:493-495`）。
  - 该入口被用于**非用户暂停**场景：身份/账号范围变化（`MainActivity.java:349`）、`/api/auth/me` 401/403（`:376`）、关闭备份开关（`:394-397`）；`BackupScreen` 在修改“备份全部相册/目录/模式/子目录/添加或移除目录”前也调用 `activity.pause()`（`BackupScreen.java:105,110,134,451,490`）。
  - 非手动启动在 `startBackup(false)` 被 `userPaused` 直接挡掉（`MainActivity.java:471`），服务端 `mayStart(explicit=false, userPaused=true)` 同样拒绝（`BackupService.java:102`）；唯一清除点是 `onStartCommand` 的 `manual=true`（`:122`）。
- 触发条件
  1. 打开“打开时自动备份”，随后修改任一备份目录/模式；或 2) 会话/凭据失效触发 `checkIdentity` 401；之后重新进入应用（或同一 owner/deployment 重新登录，scope 不变）。
- 实际影响：自动备份不再启动，直到用户显式点“立即备份”；用户看到的同步状态是“备份已暂停”，把认证失败/改设置误报成用户主动暂停。这与“用户暂停须持久化”的需求不一致（内部停止不应写用户意图）。
- 修复方向：拆分“用户暂停”和“内部停止当前运行”；仅 UI/通知按钮与显式暂停写 `userPaused`，账号切换、401、修改设置改用只置 `cancelled` 的停止路径；或在成功重新认证/重新启用时清除该 scope 的 `userPaused`。

### 2. [中] 安卓：上一轮备份的收尾 Handler 可能停掉刚启动的新一轮备份（生命周期竞态）

- 位置与证据：`BackupService.java:236-256`。`runBackup` 的 `finally` 先把 `working` 置 false（`:240`），再向主线程 post 收尾任务；该任务只检查 `current == this`，不检查是否已有新运行，随后执行 `stopForeground(...)` + `stopSelfResult(latestStartId)`（`:251-255`）。
- 触发条件：旧运行结束（已置 `working=false`）后的极短窗口内，用户点通知“继续”或 UI“立即备份”，新的 `onStartCommand` 先被主线程处理（`working=false` → 正常启动新运行），随后旧收尾任务执行。
- 实际影响：新运行的通知被移除、服务被 `stopSelfResult` 停止，`onDestroy` 置 `cancelled` 并关闭 `activeApi`，新备份随即被中断（表现为“立即继续”偶发失败）。这正好落在需求强调的“同实例暂停后立即继续等待旧任务排空”场景。
- 修复方向：为每次运行引入 epoch/startId 并在收尾任务中校验“仍是当前运行且 `!working.get()`”才 stop；新运行启动时使旧 epoch 失效；或把收尾动作放进 `onStartCommand` 的串行状态机而不是独立 post。

### 3. [低] 安卓：重启路径复用旧 `startId`，导致重启后的运行结束时服务无法真正停止

- 位置与证据：`BackupService.java:248` 以旧运行的 `startId` 直接调用 `onStartCommand(restart, 0, startId)`，该函数第 91 行会把 `latestStartId` 覆盖成旧值；重启后的运行在 `finally` 用 `latestStartId` 调 `stopSelfResult`（`:255`）。Android 只允许用最近一次 startId 停止服务，旧 id 会返回 false。
- 实际影响：通知被移除、`settings.running=false`，但服务实例仍处于 started 状态（`current` 保持非空），属于资源/生命周期泄漏；后续清理依赖系统回收。可与问题 2 一并修复。
- 修复方向：重启改用 `startForegroundService`/`startService` 让系统分配新 startId，或保留并使用最新一次投递的 startId，不把它回写成旧运行 id。

### 4. [低] 网页：新的人物筛选选项查询不会被失效，人物改名/合并/扫描后选项可能过期

- 位置与证据：新 key `['eagle', ownerId, 'PHOTO', 'people-options', includePrivate]`（`usePhotoFilterOptions.ts:14`）；`PhotoCollections.perform` 只失效 `people`、`person-review`、`person-faces`、`summary`（`PhotoCollections.tsx:69-74`）。React Query 前缀匹配中 `'people'` 不等于 `'people-options'`。
- 触发条件：展开筛选加载人物选项 → 在人物页改名/合并/扫描/改人物私密 → 回到筛选面板（30s staleTime 内）。
- 实际影响：筛选里的人名/列表可能短暂过期；不涉及权限泄漏（私密维度在 key 与服务端 grant 中）。
- 修复方向：把新 key 改为 `['eagle',owner,'PHOTO','people','options',...]` 以复用现有失效前缀，或在 `perform` 中显式失效 `people-options`。

### 5. [低] 网页：只“打开”统计日期面板就会把已选时间范围标记为“自定义”

- 位置与证据：`PhotoStatistics.tsx:63-67` 在面板打开 350ms 后自动调用 `applyDates`；`applyDates`（`:49-62`）无条件 `setPreset(dates.start||dates.end ? 'custom' : 'all')`。`dates` 初始/切换预设时与当前范围一致，因此未做任何编辑也会把“最近 1/3/5 年”按钮的 `aria-pressed` 取消、切到自定义；`onBlur` 同样触发。
- 实际影响：仅展示状态回归，查询参数通常不变；但会误导用户以为筛选被改动。
- 修复方向：仅在 `dates` 相对已应用的 `input.start/end` 真正变化时才改 `preset`，或用“用户编辑过”标志控制。

### 6. [低 / 测试缺口] 相机视频 `fps=source_fps` 只有被默认跳过的真机测试覆盖

- 位置与证据：`packages/media-core/src/index.ts:206` 在 `-vf` 中加入 `fps=source_fps`；唯一走真实 ffmpeg 的 `video-timing.test.ts` 在 `!FFMPEG_PATH || !FFPROBE_PATH` 时 skip（`video-timing.test.ts:11-16`），`video-audio-probe.test.ts` 使用假 ffmpeg 只断言参数字符串存在。报告称已在真实硬件显式路径实跑，但默认门禁不覆盖。
- 实际影响：若部署 ffmpeg 不接受该值，所有相机视频转码会失败，而常规 CI 不会发现；属于回归风险而非已证实缺陷。
- 修复方向：在可用 ffmpeg 的 CI/预发布检查中强制运行该真实转码用例（至少校验一条真实视频），或对 `fps` 表达式做启动时能力探测。
