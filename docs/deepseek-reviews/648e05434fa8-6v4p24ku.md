### 1【中】旧版颜色分析/任务会以“新版完成度”出现在处理页，违反“旧结果不能混充新版”的守卫

**文件与行号**
- `apps/api/prisma/migrations/20261101010000_eagle_basic_color_palette/migration.sql:4-7`：把旧版本颜色任务直接改成 `COMPLETED`、`completedAt=now()`、写入 `lastError='SUPERSEDED_COLOR_PROCESSOR_VERSION'`。
- `apps/api/src/eagle/eagle-processing.service.ts:46-55`：`colorCoverage` 的 `eagleAssetColorAnalysis.groupBy` 没有按 `processorVersion` 过滤。
- 同文件 `:68-70`、`:97-104`：`completedLast24Hours` 统计 24 小时内 COMPLETED 任务；返回的 `colorCoverage.processorVersion` 却是新的 `COLOR_PROCESSOR_VERSION`。
- 对照守卫正确的路径：`apps/api/src/eagle/eagle-color-query.ts:57-59` 在查询颜色时必须 `processorVersion='color-v4-eagle-basic'` 且 `analysis.assetRevision=asset.mediaRevision`。

**触发条件及证据**
迁移不修改旧 `EagleAssetColorAnalysis.isCurrent`，因此旧版分析在对应资产被新版 worker 处理前仍是 `isCurrent=true`、`status=COMPLETED`。处理页的 `groupBy` 只按 `isCurrent=true` 统计，故迁移完成、新版颜色队列尚未跑完时，`completed` 仍按旧结果计算，处理页可能显示“可用于筛选”或接近 100%；同一时刻图库颜色筛选返回的 `colorCoverage`（按新版本过滤）却可能仍是 0。迁移还会把旧 PENDING/PROCESSING/FAILED 任务计入 24 小时“已完成”，并在任务列表显示 `SUPERSEDED_COLOR_PROCESSOR_VERSION` 作为 `lastError`。

**实际影响**
这是本次版本常量升级与迁移引入的回归：运维/处理页会给出错误的新版颜色覆盖率，可能在 6 万项颜色重算尚未完成时误判“颜色筛选已可用”。不是数据删除问题，但属于可见的状态正确性问题，也会误导发布验收。现有 `eagle-processing.service.test.ts` 没有覆盖 `summary().colorCoverage`。

**修复方向**
- 处理页统计按 `processorVersion: COLOR_PROCESSOR_VERSION` 过滤，并按 `assetRevision = asset.mediaRevision` 计数（可用一条 SQL 或显式 join，不能只过滤版本）。
- 迁移把旧版本当前分析改为 `isCurrent=false`（历史行保留），或明确把旧任务标记为“退役”而不是伪造 `COMPLETED/now`；至少从“最近完成”和任务列表成功态中排除 `SUPERSEDED_*`。
- 补一条 `summary().colorCoverage` 在旧版本分析存在时仍应显示未完成的单测。

### 2【低】颜色筛选与 `offset` 组合会返回无法继续使用的 `nextCursor`

**文件与行号**
- `apps/api/src/eagle/eagle-color-page.ts:65-84`：`colorPageKey` 只排除了 `limit`、`cursor`，仍把 `offset` 算进游标绑定键。
- 同文件 `:95-96`、`:108-113`：第一页带 `offset` 时仍会返回 `nextCursor`。
- `apps/api/src/eagle/eagle.service.ts:204-205`：`offset` 与 `cursor` 同时出现直接 400。

**触发条件及证据**
请求 `GET /assets?color=#rrggbb&offset=N`（无 cursor）→ 服务端返回绑定“带 offset 的 query key”的 `nextCursor`。客户端继续翻页时：
- 若继续带 `offset` 和 `cursor`，被 `eagle.service.ts:204-205` 拒绝；
- 若按游标语义去掉 `offset` 只带 `cursor`，`decodeColorCursor` 的 `data.key !== key` 校验失败，仍 400。

因此该 `nextCursor` 在此组合下不可用。颜色页的 `LIMIT/OFFSET` 代码本身说明实现者尝试支持 offset，但游标键与“offset+cursor 禁止”的约束互相矛盾。

**实际影响**
当前网页没有使用 `offset`（`hasTimelineNavigation` 要求 `!activeFilterCount`，颜色属于活动筛选；`offset` 也不在 `assetFilters` 中），所以现阶段主要是 API 层的潜在缺陷，用户路径影响低。若桌面端或未来调用方使用“日期定位 offset + 颜色筛选再加载更多”，会直接 400。

**修复方向**
游标键不包含 `offset`（游标位置本身已编码分页边界），或在颜色筛选下明确禁用 `offset` 并相应不返回游标；同时补一条 `offset+颜色` 的回归测试。

### 3【低】相似组“全部取消保留”可以绕过前端批量清理校验，导致确认数量错误、整批被服务端拒绝

**文件与行号**
- `apps/web/src/components/eagle/EagleDuplicates.tsx:355-362`：`extraKeepCount` 对 `{removeIds: 全部成员}` 会算出 `-1`。
- 同文件 `:368`：`invalidKeeper` 只检查 `keepIds?.length === 0`，不检查 `removeIds` 覆盖整组。
- 同文件 `:668-689`（所选批量）、`:938-951`（全部筛选批量）依赖这两个值启用按钮和计算确认数量。
- 详情中的选择写入：`:1099-1110`。

**触发条件及证据**
在“原图画面相同”这类 `SIMILAR` 组中，详情默认 `keepMode=false`（`group.kind !== 'EXACT'` 且无 `initialSelection.keepIds`），用户取消勾选全部“保留此项”后得到 `{removeIds: 所有成员}` 并写入 `keepers`。此时：
- `extraKeepCount = (group.count - group.count) - 1 = -1`；
- `invalidKeeper` 为 false；
- `selectedRemoveCount`/`allRemoveCount` 反而增大，批量按钮保持可用；
- 确认框可能显示 `保留 0 项，清理 count 项`。

提交后服务端 `cleanup` 的 `keep` 集合为空，抛出“每组必须保留至少一项”，整批（包括其他正常组）被拒绝，不会误删数据，但确认信息错误且批量操作被阻塞。

**修复方向**
把“`removeIds` 覆盖整组导致保留数为 0”也纳入 `invalidKeeper`（或在 `extraKeepCount` 中钳制非负、在确认前逐组校验保留数），并在批量按钮上禁用。服务端已有兜底，保留即可。

## 待验证项（证据不足，需主代理/后续实测确认）

1. **原地编辑 recipe 是否应受“编辑保护”覆盖**
   `apps/api/src/eagle/eagle-duplicate-filters.ts:55-64` 只保护 `EagleAssetEditRecipe.baseAssetId IS NOT NULL` 的“编辑成片 + 原图”；`saveEagleEditRecipe` 产生的原地 recipe（`baseAssetId: null`）不在保护范围。文档定义的“已知编辑关系”是否包含这种原地编辑需要产品确认；若不包含则无需改，若包含则当前默认保护有遗漏。

2. **受理清理后、执行前新增编辑关系不会被二次检查**
   `eagle-duplicates.service.ts` 的 `execute` 只复核 `rowVersion`/`mediaRevision`；创建编辑副本的 `eagle-upload.service.ts:38-57` 不增加原图 `rowVersion`。因此“确认清理 → 执行前创建编辑副本”的并发窗口内，原图仍可能进入回收站（可恢复，不是永久丢失）。是否要求执行时再查一次编辑关系，需要主代理判断需求边界。

3. **拍摄时间筛选的时区/表示语义**
   `eagle-duplicate-filters.ts:23-24` 用 `capturedLocal ?? capturedAt?.toISOString()` 比较；`capturedLocal` 是不带时区的墙钟字符串。两成员分别有/没有 `capturedLocal` 时会出现“本地时间串 vs ISO 串”的假不等；不同时区同一墙钟时间也可能被当作相同。当前新测试只覆盖“都缺失”和普通字段差异，没有正向 `sameCapturedAt`、混合 `capturedLocal`/`capturedAt` 和时区用例。是否为可接受的产品语义需要确认。

4. **`allExact` 前端回退路径**
   `EagleDuplicates.tsx` 的 `confirmAll` 在 `data.verifiedGroups === undefined` 时走 `allExact` 且不带 `filters`/`keepOverrides`，会绕过筛选与编辑保护。当前服务端始终返回 `verifiedGroups`，因此只在“新网页配旧 API”场景出现；作为兼容分支是否保留需要主代理判断。
