## 2026-11-17 图库缩略图并发与内存缓存

网页网格原本以 3–4 并发、每秒 32 次启动、突发 16 拉取首屏缩略图；3440 宽屏按默认 210 像素卡片一屏约 60–90 张，仅启动速率就需要约 2–3 秒，观感是从上到下一张张补齐。本次只调整客户端内部背压与缓存容量，不降低缩略图档位、不减少一屏卡片、不改变布局，也不新增用户可见的次数限制。

- 普通连接的媒体调度改为 10 并发、每秒 96 次启动、突发 48；省流量／2G 保持 2 并发、每秒 16 次、突发 8。429／5xx 仍触发共享冷却，单图仍有 12 秒超时；到达上限时请求继续按屏幕顺序排队，不丢弃、不报错。保护对象是 NAS 上 API／MinIO 的瞬时请求和浏览器解码并发，不是用户配额。
- 按一屏 90 张、单张 5–30KB 推算，最坏约 90 次小 GET、2–3MiB 正文集中在约 1 秒；这是单用户首次浏览的突发，不是持续吞吐承诺。首屏填满时间按限速推算从约 2–3 秒降到约 0.9–1 秒，未在现网实测。
- 网页缩略图内存缓存条目由 512 提高到 2048，字节上限保持 128MiB；按单张约 20–30KB 计，常驻约 40–60MiB，不扩大既有内存预算。
- 桌面主进程上游并发由 6／队列 64 提高到 12／队列 128，只影响磁盘未命中后的联合下载；已安装客户端需重新打包才生效，网页部分不依赖客户端更新。
- 上述并发与速率为代码常量，不是环境变量；没有新增用户可调上限。每次媒体请求的 SQL／S3 路径与正文大小不变，本次不改 API、数据库、worker 或存储。
- 验证：完整 `ci:check` 通过（网页 157 个测试文件／1,205 项，桌面 33 个文件／202 项；lint、typecheck、build、架构、契约、格式与 OSS 检查均通过）；调度器新增普通连接与慢网两组默认值断言。尚未在现网测量首屏回填时间，发布后按真实样本复核。

## 2026-11-16 上传前查重与上传管理器（已发布）

网页批量导入增加两道去重：上传前由浏览器计算 SHA-256 并用现有 `check-content-batch` 查询，命中则直接标记“重复跳过”，不再 initiate、签名、PUT、complete 或走入库校验；上传后服务器仍按同一 owner、图库模式和完整内容哈希做权威去重，二者都不删除。

- 浏览器哈希最多 2 个文件并行。32MiB 及以下使用硬件加速的 WebCrypto；更大的照片、RAW 和视频按 4MiB 分块流式计算 SHA-256，内存只与分块大小相关，不再按文件大小跳过预检。没有用户可见的文件大小上限。
- 预检请求按最多 50 个文件或 80ms 合并为一次 `POST /api/(eagle|photos)/uploads/check-content-batch`，仍是一次 owner＋模式限定的 `SELECT`；查询失败时失败开放（继续上传），服务器发布事务仍会去重。
- 计算出的 SHA-256 传入 initiate 的 `contentSha256`，服务器在入库时核对实际内容，防止哈希与上传内容不一致。
- 上传管理器只改前端：总进度按已传输字节计算，速度与剩余时间每秒采样；暂停在文件之间生效，正在传的分片先完成；支持一键重试全部失败、成功／重复跳过／失败／等待分类计数、单项“重复跳过”标识和列表折叠。新增 SQL、S3、事务均为 0，状态查询继续使用原批量接口。
- 成本推算（300 张、平均 12MiB）：预检需读一遍文件并计算约 3.6GiB 哈希，按 2 路并行；重复文件可省去各自的全部分片上传与入库校验，非重复文件只多一次批量查询。真实哈希速度取决于磁盘与浏览器，未在现网测量。

验证：新增测试覆盖批量预检合并、小文件与大文件分块哈希、哈希或查询失败开放、会话中止、上传前重复跳过、服务器判重显示、暂停续传、一键重试全部失败、面板进度/分类/折叠；本轮完整 web 测试 1195 项（156 个文件）通过，lint、typecheck、web 构建与架构检查通过。该版已于 2026-11-16 以 web 镜像 `38dd0da6` 发布生产（流式指纹修正），随后以 `79800fc0` 修正“清除已结束”遗漏重复跳过项；API／存储未重建，公网首页与 readiness 200，线上与本地构建 `index.html` 一致，见[流式指纹发布记录](history/releases/main-production-release-2026-11-16-upload-streamhash.md)与[清除修复记录](history/releases/main-production-release-2026-11-16-upload-clearfix.md)。尚未在真实浏览器用大批照片实测预检耗时。

## 2026-11-16 网页批量上传吞吐（已发布）

网页批量导入的传输主路径改为并行，并停止让服务器校验占用上传位：

- 文件级并发由 2 提到 4（`UPLOAD_FILE_CONCURRENCY`），单文件内分片由串行改为最多 3 路并行（`UPLOAD_PART_CONCURRENCY`）。按 5MiB 分片计，最多 12 个分片 PUT 在途（约 60MiB 的 Blob 引用，不复制文件内容）；这是网络与 NAS 入口的真实在途数据边界，不是面向用户的配额，未新增任何用户可见的次数或数量上限。
- 分片地址仍逐片签名，但签名请求与 PUT 一起并行；单文件请求数不变（1 次 initiate、N 次 presign、N 次 PUT、1 次 complete）。
- `complete` 被服务器接受（分片已合并、对象已落盘、终结任务已入队）后立即释放上传位；入库校验在后台继续。改动前浏览器要每秒轮询该会话直到校验完成，期间占着一个上传位，而 operations 端校验一次只处理一份；300 张时这是主要排队点。
- 新增 `POST /api/(eagle|photos)/uploads/status-batch`：一次按 owner＋当前图库模式过滤的 `SELECT` 返回多条上传会话状态，替代逐会话每秒 GET。客户端在仍有待入库项时每 1.5 秒发一次批量请求，全部入库后停止。
- 界面拆成“已上传 X/Y · 入库 Z/Y”，单项传输完成后显示“已上传，入库校验中”；列表刷新仍在每批上传的入库全部结束后执行一次，没有按项刷新，也不重置分页或滚动位置。

成本对照（以 300 张、平均 12MiB、每张 3 个分片为例，均为推算）：

| 项目              | 改动前                               | 改动后                                  |
| ----------------- | ------------------------------------ | --------------------------------------- |
| 分片 PUT 并发     | 最多 2（每文件 1）                   | 最多 12（4 文件 × 3 分片）              |
| 传输完成后等待    | 占用上传位直到校验完成               | 立即释放，后台批量查询                  |
| 入库状态请求      | 每个上传位每秒 1 次 GET（最多 2/秒） | 每 1.5 秒 1 次 POST（含全部待入库会话） |
| 状态查询 SQL      | 每次 GET 1 条                        | 每次批量 1 条 `IN` 查询                 |
| complete 事务／S3 | 1 事务＋1 CompleteMultipartUpload    | 不变                                    |
| 终结任务          | 每文件 1 次 HEAD＋流式 GET＋发布事务 | 不变                                    |

安全与正确性：批量状态接口由认证主体推导 ownerId，按当前图库模式过滤；跨 owner 或不存在的会话直接不返回，不泄露存在性，并保留同源守卫；DTO 拒绝非 UUID 与 ownerId 注入。入库仍执行大小核对、SHA-256、格式检测、查重和原子发布；校验失败仍按原 10 次上限终止并显示单项错误，对象清理路径未改；取消登录或切换账号仍会中止传输与轮询。服务器端入库校验仍一次处理一份，本次只移除“它阻塞传输”的耦合，没有提高校验并发。

验证：新增单元测试覆盖文件并发峰值 4、传完即释放上传位、批量状态一次请求、分片乱序完成仍按编号提交、会话撤销仍中止 PUT；API 测试覆盖 owner／模式过滤与同源守卫。本轮完整 web 测试通过 1175 项（153 个文件），API 测试 677 项（676 通过、1 跳过），全仓 lint、typecheck、web 构建、架构检查与 `contracts:generate` 均通过。该版已于 2026-11-16 以 `811ead5b` 发布生产：API／operations／library-reader／web 四容器 healthy、0 重启，公网首页与 readiness 200，匿名状态路由 401，见[发布记录](history/releases/main-production-release-2026-11-16-upload-throughput.md)。尚未在现网 NAS 或公网链路测量端到端吞吐，上述并发数字是代码路径与单测断言，不是生产 p95。

## 2026-11-15 人脸整理批量、分组修正与扫描状态（源码候选）

人物页的 `PHOTO_PEOPLE_SCAN` 不再要求执行容器安装本地人脸模型：该后台命令只做一次集合入队，真正的 `ANALYZE_PHOTO_FACES` 仍由具备 faces 能力的媒体节点领取。此前 API 进程有模型变量、operations 执行进程没有，导致人物页扫描在后台直接失败；修正后扫描命令仍为原一次事务／一次集合 INSERT／零 S3，单张照片的人脸计算成本不变，只是不再被执行环境误拒。

人物代表脸从“第一张脸永久冻结”改为按匹配结果做有限指数移动：同一发布事务内先累积混合向量，再对每个命中分组只更新一次 `EaglePhotoPerson.prototype`，不按人脸数增加 person 更新；不新增事务、队列项或 S3 请求。新分组仍只写入第一张脸的向量。该更新仍会触发每批每分组一次 `PEOPLE` workspace 通知；相比逐脸更新已把通知和写语句从人脸数降到命中分组数，但不能声称完全不产生通知。合并人物时用参与合并的原型均值重算目标，纠正／移除人脸时最多采样 32 张现行人脸重算受影响分组；这些是用户级低频操作，代价随一次纠正涉及的分组数增长，不随全库照片数增长。`rowVersion` 不因自动原型更新递增，避免普通新照片写入让正在整理的用户合并冲突。原型更新会改变后续匹配结果，属于有意的行为修正；实际错误合并率仍需用真实图库样本另行评估，不能把本次单测当成识别准确率提升证明。

待确认队列只取未命名分组，并在证据层加入默认 `0.30` 的相似度下限（`PHOTO_PEOPLE_REVIEW_MIN_SIMILARITY` 可调，0～1），按相似度降序而不是照片数排序。候选 SQL 和证据读取次数不变，低相似度配对在返回前被丢弃；这只减少人工确认量，不改变任何人脸向量、模型版本或已保存的“不是同一个人”决定。调低阈值会扩大确认队列，调高会漏掉真实拆分；该阈值是产品排序参数，不是并发或数量上限。

人物详情新增一次批量命令：选中 N 张人脸做“分开为不同人物”时，一个 HTTP 请求、一个 `METADATA_COMMAND` 操作、一个事务，按 N 张各建一个新分组并更新人脸；admission 另按 ID 分批一次可见性 count 用于立即返回 404，执行事务内再次校验；做“不是人脸”时同一事务内一次集合 `isCurrent=false`、按受影响分组采样重算原型、删除空分组。每个仍有剩余人脸的旧分组另有一次最多 32 张的采样读取，用于重算代表脸；数量随选中的旧分组数增长，不随全库照片数增长。原先逐张操作会发 N 个请求和 N 个后台操作；现在随选择人数增长的只有本次事务内的 N 次分组写入，不新增用户手动分批上限。两个动作都可能让照片从私密分组变为公开，操作完成时沿用原隐私投影清理和桌面缓存清理。

扫描开始后人物页只观察本地操作缓存中的扫描回执，不额外发 SQL；扫描命令完成后人物目录与计数在最多 2 分钟内每 5 秒刷新一次（至多各 24 次读取），随后停止，用户仍可用“刷新”。没有新增按资源数增长的后台轮询。

已命名分组搜索和合并目标搜索是在原人物目录读取上加一个 `name ILIKE` 条件，仍为一个分页 GET／一次只读查询、零 S3；采用现有 owner／模式索引，不新增常驻索引。搜索只覆盖已命名分组，未命名分组仍用位置稳定的短标识和待确认队列处理。以上为源码路径和单测口径，尚未在现用生产库测量真实人物识别准确率、端到端事务耗时或 p95。

## 2026-11-03 空闲容器巡检

空闲时不应为了反复确认同一健康状态而持续写入机械盘。NAS现场已捕获dockerd对容器状态临时文件的`fsync`；Docker进程写入随巡检次数48→6次／分钟由0.834降到0.095 MB/s（约8.8倍），方向与次数一致，属实测推断而非逐次探测都落盘的直接证明。六个现用服务原为PostgreSQL／MinIO每5秒、API／operations／web／reader每10秒，理论合计48次／分钟；统一默认60秒后为6次／分钟，减少87.5%，仍保留各自真实检查命令，三次连续失败标记unhealthy。Docker不会仅因unhealthy自动重启；实际进程退出仍由原restart策略处理。默认持久故障标记约三分钟，首次ready可能等待一个巡检周期，这是降低HDD空闲成本的明确取舍。

`SEKEREAGLE_HEALTHCHECK_INTERVAL`可调整巡检间隔，默认`60s`；它不是用户操作数量上限，不改变照片处理、队列唤醒、数据库持久化或隐私／租约守卫。一次API ready仍为1条`SELECT 1`、1次S3 HEAD bucket、0业务写事务、0前端刷新；按默认周期推算由每分钟各6次降为各1次。其他探测命令保持，不能把全部Docker元数据或文件系统写入都计为应用SQL。上传恢复全表扫描是另一个读取成本，本配置变更不声称已消除。生产对照和计数层级限制见现用运行文档。

同轮排查剩余周期性CPU：业务worker在没有通知时每30秒回退轮询`buildMediaWakeQuery`。`EagleMediaJob`保留全部完成／失败历史，默认20%阈值让统计在两天后才更新；统计陈旧时该查询估算出数千条待办，改为对整个`EagleAsset`（13.4万行、约1.05万页）做哈希连接，单次约1.2秒、约占3个核，30秒一次正好形成DSM图上约3%的锯齿。手动`ANALYZE`后成本48129→177、实测1.2秒→约0.5毫秒（约400页），说明是计划退化而非查询本身必然昂贵。新增迁移 `20261103130000_hot_table_autovacuum_tuning` 为两张热表收紧`autovacuum_vacuum_scale_factor=0.05`、`autovacuum_analyze_scale_factor=0.02`（`EagleMediaJob`另设`cost_limit=800`），只改表级自动清理阈值，不改变查询语义、队列或保留策略；生产已先按同参数设置并`VACUUM (ANALYZE)`清掉7.7万死元组。该结论只覆盖数据库侧周期负载；DSM自身服务（Universal Search索引、`scemd`、SNMP、aMule）的CPU与写回仍独立存在，未用本项修复冒充已消除。

- **SQL 语句数**：按一条 / 一张 / 一批统计，不用「大概很快」代替。
- **S3 请求数**：HEAD、COPY、GET、PUT 分开统计。
- **事务数与持锁时间**：尤其是 privacy advisory lock、行锁。
- **前端请求数与上下文**：是否重置分页/滚动/选择。
- **墙钟时间**：p50 / p95，注明数据规模和 MinIO 位置。

## 3. 怎么测量（只读）

1. **S3**：MinIO 的 `minio_http_requests_total`（按 method/API），或 `mc admin trace`（若本机有 `mc`）；统计一次发送的 HEAD/COPY 次数，与「对象数 × 2」对照。
2. **SQL**：Prisma 查询日志或 `pg_stat_statements`；按 operation/asset 过滤，统计单张语句数与耗时。
3. **墙钟**：浏览器或 `curl -w '%{time_total}'`；发 1 张、10 张、100 张，记录数据规模与图片像素。
4. **前端**：Network 面板看 assets/operations 请求频率；检查缓存 `pages` 是否被截成 1、滚动是否跳。
5. **锁**：发送时 `pg_stat_activity` 看 `wait_event='advisory'` 和事务时长。

## 2026-10-31 删除结果自动同步修订

用户明确否定“后台完成后手动加载更新”。两个模式共用原查询缓存，删除、恢复、清空和发送成功发布后自动重取当前活跃查询，保留读取中的全部旧页、卡片及滚动；未打开的查询只失效，返回时再更新。服务端部分失败时以真实列表结果为准，不能按入队选择把失败项一起隐藏。

成本：原操作入队、领取与发布的SQL、事务、S3成本不变；本次前端不直接新增写事务或S3操作。每轮列表读取最多为当前已加载P页各一次GET（后续游标按新结果重建，避免删除造成分页缺口），另有当前活跃计数／关系查询各一次；并非一张删除一轮。一次状态响应合并同模式进度，中间发布每模式至多10秒启动一轮，整批结束立即同步；在途读取不取消，期间新发布合并成随后一轮，保证最终事实不漏。没有打开的历史筛选不发请求。大量已加载页仍有P次读取成本，本轮未引入服务端增量协议，不能声称常数成本或实测大库延迟；不得以截成第一页或要求手动刷新规避成本。

## 2026-10-31 即时删除与撤销候选（未发布）

本轮用户要求暂不推送生产。删除主图库采用一次意图投影及一次终态回执应用，终态不再重新读取P页资产。回执按原SQL批次配置分页（默认512个操作项、自动继续）；每页一次作用域操作读取、一次状态聚合、一次回执读取，另按同一内部SQL批次读取当前资源成员状态（包括失败、跳过和已不存在的项），无S3请求，不返回描述、对象键或人脸／EXIF。当前活跃计数、标签与查重结果按同轮终态合并校准；恢复或发送目标最多补读当前列表首窗口并合并旧页，不丢页或旧游标。查重列表仍须按同一个新revision重建已加载组分页，成本与主图库局部更新分别记录，不能冒充全系统常数请求。

撤销准入为短事务：权限读取与幂等关系复用、取消未领取项并登记一个恢复控制项；实际资源恢复留在独立进程，按既有元数据批次执行，无直接对象存储I/O。控制项按源已提交事实原子替换，失败、跳过、取消项不恢复；版本变化单独失败。显式外键防跨owner／模式补偿，唯一关系防重复撤销。新增迁移仅增加可空关系、唯一索引、作用域外键及动作CHECK，现用生产尚未迁移。

隔离六万选择诊断复现：重复IN批次在未分析的新图库选择了低估owner范围的通用预备计划，原120秒准入预算耗尽；禁用JIT没有改善。保持相同数据、批次和120秒预算，仅事务级值相关计划的对照为8.442秒、478条SQL、0次存储复制（另含一个诊断SET语句），不是生产p95。候选对超过内部SQL批次的选择采用SET LOCAL plan_cache_mode=force_custom_plan，不改变全局规划器、权限或用户数量；最终未插入诊断包装器的回归另行记录。

最终无诊断包装器的隔离回归：六万项一次入队8.787秒／479条SQL／0次S3复制（另一次并行构建期间为11.493秒）。这是本机合成数据单次结果，不是NAS或生产p95。六万库查重首屏176.998毫秒／12条SQL，100组清理准入14条SQL／0次对象读取，既有预算未放宽。测试以同一数据库串行执行隔离夹具，Prisma查询事件在测量前后排空，避免上一阶段异步日志污染SQL计数。

独立operations新增一条PostgreSQL LISTEN连接，API没有监听、后台执行或轮询定时器。每次入队、重试、撤销与查重准入在原事务内多一个固定通知SQL；通知仅含模式，提交后唤醒对应执行器。断线保留原5秒恢复轮询并重连，不丢意图。`EAGLE_OPERATION_WAKEUP_CONNECT_TIMEOUT_MS`默认3000毫秒，限制连接占用启动等待；到顶后继续原轮询并重连。`EAGLE_OPERATION_WAKEUP_RETRY_MAX_MS`默认30000毫秒，限制失败重连频率占用；到顶按此间隔重试，任务继续由原轮询发现。两项均可用同名环境变量调整，不改变用户选择数量。

## 2026年11月1日基础颜色筛选本地候选

## 2026年11月1日刷新效率

### 2026-11-02 常驻读取修订候选

## 2026年11月14日 上传校验异步化

上传完成不再在 API 进程内读取原图：`complete` 只合并分片、写 `UploadFinalizationJob` 并向 operations 发 NOTIFY；operations 一次领取一个任务，流式落盘并只读文件头。每次受理为 1 事务（会话更新＋任务 upsert＋NOTIFY）与 1 次 CompleteMultipartUpload；每次任务为 1 次领取更新、1 次会话读取、1 次 HEAD、1 次流式 GET 和原发布事务，另有 1 次任务状态更新。客户端在校验期间每秒读取一次会话，完成后读取资源并失效一次列表；不重放已加载分页。

本机同代码路径实测：111MP PNG 检查峰值从 710–785MB 降到约 104MB；50MP／34MB JPEG 从 133MB 降到约 104MB。临时文件一次只有一个，大小受原上传声明与现有媒体上限约束。上述为代码路径与本机样本，真实数据库计数以 `test:library-integration` 为准，不冒充 NAS 生产 p95。设计与验证步骤见[上传校验异步化](history/records/upload-finalization-2026-11-14.md)。

## 2026年11月15日 安卓释放空间

旧流程对每个候选重读整文件并重算 SHA-256，再单独请求一次 `check-content`；扫描和删除前各做一遍，SAF 文档删除前还有第三遍。500 项、约 13GB 的计划约为 26GB 读盘/哈希、约 1,000 次 HTTP 请求和数千次媒体库游标查询。

新流程一遍扫描先读备份收据与文件 size/mtime，每 500 项合并为一次 `check-content-batch`（一条行值 `IN` SQL，owner/模式/删除/私密过滤不变）；删除某一批前对这批最多 500 项各读取一次并核对内容哈希，同时再批量确认服务器副本。500 项一批的 HTTP 从约 1,000 次降到约 2 次，原文件读取从两遍降到一遍，且不会对整个图库预先读取。计划按每批最多 500 项或 10GB（十进制）切分，批次之间保留计划继续，不再重复扫描；时间筛选按文件日期。真实端到端耗时以安卓实机回归为准，不把本机 JVM／真实数据库样本当成生产 p95。

## 2026年11月15日 操作进度计数器与导入批量（本地候选，未部署）

`EagleAssetOperation` 新增 queued／running／completed／skipped／failed／cancelled 权重列，由 `EagleAssetOperationItem` 的语句级触发器在同一事务内维护；`list`、`results`、`retry`、`cancel` 读取计数器，仅按覆盖索引聚合 FAILED 行的错误码，不再在每次进度轮询时聚合全部 item。迁移先回填现有操作再创建触发器；一次 `createMany`／`updateMany` 只触发一次按批聚合，不是逐行更新。

导入 `METADATA_UPDATE` 改为每 100 项一个独立事务；标签、注释、来源与关联使用集合 SQL／`createMany` 摊销，不再把整个 preflight 放在单一 120 秒事务里逐项写入。部分页提交后可从剩余 STAGED 项重试续做，已完成项不会重复写入。清单数量／字节数和缺失文件夹在同步前先校验，非法清单不会改动素材；每页事务锁住 run 并复核 CANCELLED，页面与取消不会互相覆盖；同一 run 的并发预检在单实例 API 内串行。

前端批量修改、标签、批量成片与编辑上下文请求和网关统一使用 150 秒受理预算；标签改名／删除不再清空整账号桌面缓存，只有实际改变可见性的命令才清空。

成本与验证：计数器在入队／领取／发布的原事务内增加一次按批聚合 UPDATE；跨页读取由 O(items) 降为常数行加 FAILED 错误码行。真实数据库集成测试覆盖迁移、历史升级与完整恢复；本机样本不代表 NAS p95。

废弃发送计划的删除 outbox 保留延迟复制兜底，但增加 `cleanupAttempts` 上限 30 次：每天重试一次，超过后不再生成新的删除行，避免永久循环；已有集成测试的“第二次重试必须重新入队”语义保持不变。

同轮补充：操作行新增 `errorCounts`，失败路径与 item 状态同事务按错误码累加，轮询不再查询 item 表；`retry` 重置失败项时同时清空。读取宿主改为 `EagleLibraryReadState` 提交通知触发同步，保留 30 秒兜底轮询，不再每秒查询。带资源选择的命令按「选中资源是否含私密」标记操作私密性，无资源选择的命令仍沿用主体授权范围。API 运行镜像改为仅生产依赖，迁移所需 Prisma CLI 单独安装；本机镜像从 4.29GB 降到 4.1GB，剩余体积主要来自 ffmpeg/RAW/Python 媒体工具而非 devDependencies。均为本地候选，未部署。
