## 2026-11-03 空闲容器巡检

空闲时不应为了反复确认同一健康状态而持续写入机械盘。NAS现场已捕获dockerd对容器状态临时文件的`fsync`；Docker进程写入随巡检次数48→6次／分钟由0.834降到0.095 MB/s（约8.8倍），方向与次数一致，属实测推断而非逐次探测都落盘的直接证明。六个现用服务原为PostgreSQL／MinIO每5秒、API／operations／web／reader每10秒，理论合计48次／分钟；统一默认60秒后为6次／分钟，减少87.5%，仍保留各自真实检查命令，三次连续失败标记unhealthy。Docker不会仅因unhealthy自动重启；实际进程退出仍由原restart策略处理。默认持久故障标记约三分钟，首次ready可能等待一个巡检周期，这是降低HDD空闲成本的明确取舍。

`SEKEREAGLE_HEALTHCHECK_INTERVAL`可调整巡检间隔，默认`60s`；它不是用户操作数量上限，不改变照片处理、队列唤醒、数据库持久化或隐私／租约守卫。一次API ready仍为1条`SELECT 1`、1次S3 HEAD bucket、0业务写事务、0前端刷新；按默认周期推算由每分钟各6次降为各1次。其他探测命令保持，不能把全部Docker元数据或文件系统写入都计为应用SQL。上传恢复全表扫描是另一个读取成本，本配置变更不声称已消除。生产对照和计数层级限制见现用运行文档。

同轮上传替换清理索引：恢复服务每分钟分别检查两个模式的`retiredObjectKeys`。新部分索引只收录非空待清理键，保留原Prisma查询、模式／关系守卫、重试与原对象清理流程，不新建业务队列，不删除上传历史或延后真实恢复。此阶段空队列仍是1次SELECT／每模式、0次S3及0次业务更新；有待办仍按原每会话／每旧对象执行清理和回执，新增SQL／事务／前端刷新均为0。索引仅在待清理状态进入／离开时维护，不给全部已完成上传各存一份候选。迁移并发建索引，建索引的一次性历史扫描不能计为空闲开销。

`upload-recovery-performance.test.mjs`通过真实服务调用的驱动边界捕获SQL及参数，测量原查询而非手写等价语句；夹具同时包含12万份资源和12万份已完成上传、每模式六万份，避免小资源表被规划器短路而产生虚假通过。MATERIAL空结果访问5196页的RED已执行；添加索引后MATERIAL为2页、PHOTO为1页，约束低于64页；两模式实际待清理项均完成。页数为数据库缓冲页访问，不能当作物理盘读取字节或NAS延迟承诺。回归已接入`test:library-integration`，测试执行仅处理自己的合成清理项；完整生产迁移／镜像与恢复验收状态见现用运行文档。

同轮额外发现两个脱离父会话、运行约40分钟的`docker system df`调用（其中一个接`head`）。捕获到daemon对MinIO金字塔目录的`getdents64`全树遍历，同时卷为`relatime`且内核处理Btrfs延迟引用释放；对应时段阵列约9 MB/s写入，不得把这段算作已恢复的空闲状态，也不能全部归因应用业务写入。取消这两个只读统计及孤立等待shell后复测；没有停止图库或删除对象。未在项目应用／部署脚本发现自动调用该命令，原发起会话已丢失，不能猜测发起者。

日常健康、运行状态和部署空间预检使用挂载点`df`、容器实例元数据或数据库大小统计；除非用户明确要求完整容量盘点，不默认执行`docker system df`或对整个对象卷做`du`。`--format`、管道`head`、`du --max-depth`只改变输出，不能限制底层全树访问量。此类扫描的成本随原件、派生、切片与MinIO对象目录总数增长，SQL和S3请求可以为0却仍产生大量文件系统工作；它不是常数成本的“轻量诊断”。

## 2026-11-02 日期搜索往返摊销

普通日期搜索不再每64～1000个未筛选资源往返一次数据库。匹配、原精确向量距离及日期／ID分页在同一SQL内完成，只有名称／标签时复用原可索引的候选查询；不增加内存副本、后台进程、业务事务、用户数量上限或近似召回。每次排名调用固定1条SQL，原文本向量准备、卡片投影、实况和照片堆叠成本保留，S3直接调用0，前端仍一次列表GET并追加原分页。它不把多轮并发失效后的卡片补齐说成整个请求永远一次查询。

网页／桌面默认相关度搜图也将主详情候选从固定250改为当前页所缺数量加1，正常40项页面读取41份详情；并发失效时仅补齐缺项，堆叠封面保持原成本。原SQL数通常不变，但主详情数据量减少83.6%；真实NAS日志的详情语句耗时合计约79→43～46毫秒，包含并行语句，不冒充完整请求提速。向量排名仍主导完整调用，素材总耗时波动未证实稳定改善，全部样本及限制见本轮复核。

真实NAS只读数据层对照：58,338份照片和64,706份素材，空结果分别由365／368条排名SQL降到1条；两个方向交替样本、已有向量的密集／稀疏匹配及结果摘要见[运行效率复核](runtime-efficiency-2026-11-02.md)。六万份隔离回归验证空结果、超过千项的完整分页及主体／模式／私密／回收隔离。向量稀疏查询仍可能读取大部分向量，不能由消除往返承诺任意搜索毫秒返回；未增加原始向量常驻内存或放宽查询／模型时限。

## 3. 怎么测量（只读）

1. **S3**：MinIO 的 `minio_http_requests_total`（按 method/API），或 `mc admin trace`（若本机有 `mc`）；统计一次发送的 HEAD/COPY 次数，与「对象数 × 2」对照。
2. **SQL**：Prisma 查询日志或 `pg_stat_statements`；按 operation/asset 过滤，统计单张语句数与耗时。
3. **墙钟**：浏览器或 `curl -w '%{time_total}'`；发 1 张、10 张、100 张，记录数据规模与图片像素。
4. **前端**：Network 面板看 assets/operations 请求频率；检查缓存 `pages` 是否被截成 1、滚动是否跳。
5. **锁**：发送时 `pg_stat_activity` 看 `wait_event='advisory'` 和事务时长。

## 2026-10-31 删除结果自动同步修订

用户明确否定“后台完成后手动加载更新”。两个模式共用原查询缓存，删除、恢复、清空和发送成功发布后自动重取当前活跃查询，保留读取中的全部旧页、卡片及滚动；未打开的查询只失效，返回时再更新。服务端部分失败时以真实列表结果为准，不能按入队选择把失败项一起隐藏。

成本：原操作入队、领取与发布的SQL、事务、S3成本不变；本次前端不直接新增写事务或S3操作。每轮列表读取最多为当前已加载P页各一次GET（后续游标按新结果重建，避免删除造成分页缺口），另有当前活跃计数／关系查询各一次；并非一张删除一轮。一次状态响应合并同模式进度，中间发布每模式至多10秒启动一轮，整批结束立即同步；在途读取不取消，期间新发布合并成随后一轮，保证最终事实不漏。没有打开的历史筛选不发请求。大量已加载页仍有P次读取成本，本轮未引入服务端增量协议，不能声称常数成本或实测大库延迟；不得以截成第一页或要求手动刷新规避成本。

## 2026-10-31 即时删除与撤销候选（未发布）
