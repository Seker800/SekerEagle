# 照片智能整理与 MCP 实施计划

状态：首轮代码已在本机实现并进行隔离验证；真实模型质量与个人图库试点待进行。记录日期：2026-10-20。

当前接入方式、支持范围与验证结果见 [本机使用与验证](photo-agent.md)。

目标是让用户向 Agent 交代一个整理任务，由 Agent 查阅照片、组合证据、生成可审阅的建议，再通过受控工具执行。首轮包含两项任务：参考同期手机照片，为缺少 GPS 的相机照片补充城市级位置；识别照片库中明显不属于个人照片的内容，审核后剔除。两项任务共用 MCP 工具入口、建议记录和批量操作能力，不另建一套图库。

本计划最初作为待办保存，随后用户明确授权直接修改代码、仅本机测试且不动生产。首轮使用 stdio MCP 和独立本机测试资源实现，不扫描真实个人图库、不补跑全库模型、不迁移或部署生产，也不设置自动执行或提醒。

## 1. 讨论结论与实施默认值

| 项目       | 本次确定的方向                                        | 后续实施默认值与待验证内容                                                            |
| ---------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Agent 入口 | 希望以自然语言灵活交代整理工作，通过 MCP 提供图库能力 | 先接入一个支持工具调用和图片输入的 Agent 客户端；具体客户端、模型与传输方式开工时确认 |
| 补充位置   | 利用同期手机 GPS、相机时间及其他线索提出定位建议      | 第一版仅到城市，不把城市中心坐标当作拍摄坐标；判断不了就留空                          |
| 定位状态   | 区分设备记录、推断定位、已确认的推断定位              | 原始信息与推断分开保存；确认不改变来源；允许人工填写和纠正                            |
| 非照片识别 | 结合文件名比对及现有 2B 视觉向量筛选                  | 向量只做候选召回和排序；结合画面复核，不把相似度视为分类概率                          |
| 剔除方式   | 从照片库移除不需要的内容                              | 默认先审核，接受后进照片回收站；希望保留为素材时显式选择“发送到素材”                  |

| 标签定位   | 标签可补充个人意义和用途，不要求每张照片打标签        | 本轮不建立完整标签分类体系，不把定位、确认状态塞进人工标签                            |

以上默认值用于让未来实现可启动、可验收；已实现部分以本机使用文档为准，不代表已经在真实图库上验证准确率。具体按钮位置、批次大小、阈值、城市数据源和 Agent 连接方式在阶段 0 冻结。

## 2. 用户使用流程

### 2.1 为一次出游补充城市

用户指定日期范围，说：“参考这几天的手机照片，给没有位置的相机照片补一下城市。”

Agent 分页读取这段时间的候选照片、拍摄时间、时区状态、设备和原始位置，按需查看预览；查找手机与相机之间可比对的场景，检查时间偏差，将候选照片划分到有证据支持的城市。Agent 返回分批建议，展示照片、建议城市、依据和无法确定的项目。用户可以接受整批、接受部分、改城市或拒绝；接受后保存推断来源和确认记录，随后可按城市查询，地图明确显示城市级信息。

例如：“这些照片建议归入苏州，依据为同期手机照片及相符场景；另外几张跨城市移动期间的照片无法确定。”此处城市仅为交互示例，不是检测结果。

### 2.2 清理明显不是个人照片的内容

用户指定范围，说：“找出这批照片里的截图、海报和界面素材，先给我看看。”

Agent 使用文件名线索与 2B 视觉向量分别召回候选，合并去重后查看候选预览和必要上下文，输出“建议剔除”“需要判断”“建议保留”，并附原因。用户审核后，默认将接受项移入当前照片模式的回收站；需要保留为素材的项目由用户显式选择“发送到素材”。

模糊或冲突样本不强行判定。用户拒绝后，同一媒体版本的相同建议不反复出现；模型升级或证据变化导致的新建议须说明变化，不覆盖人工决定。

## 3. 定位数据与判断规则

### 3.1 信息分层

定位来源、确认状态和精度是独立维度，避免把所有状态写进一个枚举。

| 维度         | 设计要求                                                                              |
| ------------ | ------------------------------------------------------------------------------------- |
| 原始记录     | 保留设备 EXIF GPS、拍摄钟面时间和已有时区信息；称为“原始 GPS”，不承诺设备记录绝对准确 |
| 补充位置来源 | Agent 推断或人工填写；与原始记录独立保存                                              |
| 确认状态     | 待确认、已接受、已拒绝、已失效；人工更正保留历史                                      |
| 精度         | 第一版补充位置只支持城市；原始 GPS 仍可保持坐标精度                                   |
| 城市身份     | 保存可稳定识别的城市及国家、上级行政区和数据源版本，避免同名城市混淆                  |
| 证据         | 参考资源及版本、采用的时间校正、判断理由、模型和策略版本、任务与操作者                |

“推断位置 · 已确认”仍是推断来源。用户可以设置人工位置作为当前展示位置，但原始 GPS 不被覆盖；若两者冲突，详情同时可见来源和差异。没有人工覆盖时，原始 GPS 优先；已接受推断可补充缺失位置，待确认建议不混入普通地图和城市筛选。批处理默认只补缺失项，保留既有人工决定。

城市级位置不是一个精确拍摄点。地图使用城市级聚合、范围或带明确城市标识的代表点，不把代表点展示成设备 GPS。城市筛选的事实来源与原始 GPS、已接受补充位置统一定义，待确认建议有独立审核入口，不另造一套普通筛选器。

### 3.2 推断过程

1. 冻结用户指定范围，分别读取手机位置锚点与缺失位置的相机照片；导入时间不能冒充拍摄时间。
2. 检查时区与设备时钟。同场景照片可以提出时间偏移假设；单个设备的假设仅在本次有效会话或有证据支持的时间段应用，不推广到全部历史照片。
3. 结合多个时间与位置锚点划分行程片段。手机照片是稀疏采样，不能当成连续 GPS 轨迹；相同日期、相近时间都不能单独证明同城。
4. 通过视觉向量找相似场景，必要时由具备图片理解能力的 Agent 复核。相似建筑、人物或风景仅是补充证据，不能单独证明具体地点。
5. 多线索一致时提出城市建议；跨城市移动、时间缺失、时区未知且无法校准、手机可能由他人携带或证据冲突时，保留未知或请求用户补一个关键线索。
6. 保存建议及依据，经接受后作为补充位置生效；不写回 EXIF，不改变原片，不默认修改照片时间线。

时钟偏移计算、地理归属与距离计算由确定性程序完成，Agent 负责选择证据、组织步骤和解释。不能将模型口述的置信度作为统计概率；审核时主要呈现可核对的证据。

## 4. 非照片候选检测

### 4.1 分类边界

初始候选类别为屏幕截图、聊天截图、海报、界面设计、图标、插画及文档扫描。类别用于审核排序，不直接决定删除；文档扫描是否保留、拍摄的纸张是否属于照片，需结合用户目标确定。

个人拍摄的视频、RAW、Live Photo、修图成片、拼图、翻拍老照片、拍到屏幕或海报的实景照片，以及外观接近真实摄影的生成图片，都不能仅凭格式、文件名或一个向量阈值认定为应剔除。不能因为缺少 EXIF、GPS 或相机型号就判断不是照片。

### 4.2 检测链路

- 文件名：使用截图命名等明确模式、用户给定的词及已确认样本作为线索；普通 IMG、DSC 名称或重命名情况保持中性。名称召回与视觉召回独立运行，避免单一线索漏检。
- 视觉向量：复用现有 Qwen3-VL-Embedding-2B 当前图片向量，用多组类别描述及审核过的代表样本进行比较；正反例共同参与评估。只读取 READY、isCurrent、当前 assetRevision 且空间兼容的向量。
- 画面复核：Agent 按需查看当前派生预览，比较候选类别与保留类别。2B embedding 模型输出向量，不将它当作可以直接解释图片、给出可靠分类的对话模型；若 Agent 无法看图，明确退回证据有限的候选清单。
- 输出建议：保留每条文件名线索、相似度、画面判断及冲突信息。阈值按标注样本校准，不复用普通搜索的默认最低相似度作为分类阈值。
- 故障降级：缺向量、版本不兼容或模型离线时明确标记未分析，仍可提供名称候选；不将“没有召回”解释为“确认是照片”，不自动全库补跑向量或启用 8B 打标。

目标优先减少误剔除，允许漏掉一部分非照片；不以候选命中率高为理由牺牲真实照片保留。人工审核数据可帮助未来改进召回，但本轮不自动训练模型或将用户图片外传。

## 5. MCP 与应用架构

MCP 是 Agent 访问图库的适配层。业务规则和事务仍归应用服务；网页或未来其他入口复用同一应用能力，不复制通用 Controller、provider、图库、卡片、上传、回收站或跨库发送实现。

依赖方向：Agent 客户端 → MCP 适配器 → 应用服务 → 领域规则与窄端口 → PostgreSQL、对象存储和模型适配器。

建议首轮工具契约如下；工具名仅为职责说明，最终命名在契约设计时确定。

| 能力                   | 约束                                                                   |
| ---------------------- | ---------------------------------------------------------------------- |
| 查询照片与元数据       | 有界分页、明确日期与筛选、不可变 PHOTO 作用域；按需返回字段            |
| 读取照片预览           | 读取当前鉴权派生媒体；限制大小和数量，不提供长期公开原图地址           |
| 查询位置锚点与相似候选 | 共用安全查询与向量空间规则，不直接暴露 SQL 或任意数据库能力            |
| 创建整理任务及建议     | 固定范围、版本、策略、证据；只创建建议，不隐式改照片                   |
| 预览批量变更           | 返回明确资源清单、效果、冲突和计划版本；计划属于当前认证主体           |
| 应用审核结果           | 应用明确接受的建议 ID 与操作类型；补位置、回收、发送到素材分别明确授权 |
| 任务状态与取消         | 报告进度、成功、失败和未分析项；取消阻止尚未执行项，已成功项可追溯     |
| 撤销本次操作           | 补位置与回收按版本检测冲突；跨库发送按既有移动语义提供恢复方案         |

### 5.1 权限和操作可靠性

- ownerId 从认证主体推导，DTO 不接受 ownerId；跨 owner 或跨模式按 ID 访问统一 404。Agent 不能通过自己声明 owner、模式或计划 ID 扩大权限。
- 连接按读元数据、读预览、生成建议和应用变更分权；使用可撤销、有限权限的凭据。具体认证方案根据选定传输方式设计，不直接复用 Cookie 字符串或暴露数据库、MinIO、模型端口。
- 私密资源继续要求有效私密授权；任务和应用阶段都复核授权，不因已生成建议而延长私密访问。照片名、描述、OCR 和图片里的指令都是待分析数据，不能改变工具权限或执行计划。
- 外部 Agent、云端模型会接触哪些元数据和预览必须在接入配置中明确。默认不主动上传到新云服务；本地向量检索不意味着外部 Agent 推理也发生在本地。
- 写操作必须绑定具体预览计划及已接受项目，校验计划期限、媒体版本、回收状态和最新人工决定；发生变化的项标记冲突，不覆盖后来的修改。预览后新加入范围的照片不自动进入本次执行。
- 操作有幂等键与逐项结果，超时重试只补未完成项，不能重复发送或重复移入回收站。补位置可撤销为此前状态；有并发修改时提示冲突，不盲目回滚。
- 本轮不暴露永久删除、清空回收站、任意脚本执行、直接数据库写入或任意外部网址抓取工具。

### 5.2 剔除与发送的区别

移入回收站复用当前 owner、PHOTO、私密范围内的共用操作。照片组按实际接受的成员执行，不因为接受封面就处理全组；Live Photo 的配对组件沿用现有整体语义。

“发送到素材”必须由用户显式选择，复用已有共用发送服务：创建独立目标资源和对象，成功后源照片入回收站，失败保持源项；不原地改模式，不复制源标签、人物、分组或定位建议关系，私密继承沿用现有规则。

跨库发送不能承诺通过简单反向发送精确撤销。恢复需识别本次目标与源回收项，检查目标是否被编辑，保留独立资源边界；若首轮无法提供经过验证的补偿恢复，MCP 首轮只开放回收，不开放发送工具，仍可引导用户使用既有界面显式发送。

## 6. 建议与任务持久化

概念上分为整理任务、逐项建议和操作记录；具体 Prisma 模型在设计阶段确定，不预先锁定表名。

- 任务记录 owner、模式、发起人、任务类型、冻结范围、模型和策略版本、状态、取消标记及汇总计数。
- 建议记录目标资源及媒体版本、原状态快照、建议值、依据、参考资源及版本、审核决定与时间、失效原因和实际应用状态。审核接受与成功写入分别记录，防止失败被显示为已完成。
- 操作记录幂等身份、计划版本、逐项结果、前后值、冲突、错误和可恢复信息。建议源照片被删除、替换或失去访问授权时须重新验证；证据展示也不能泄露现已不可见的资源。
- 支持分页审核及任务恢复；审计只保存必要信息，不记录凭据、原片内容或模型隐私日志。数据库备份包含确认记录与补充位置，模型升级和元数据重提取不覆盖人工确认。

| 6 后续扩展评审   | 根据试点决定是否支持全库任务、更细定位、出游事件、标签建议及其他客户端                                                               | 单独确认扩展范围与上线，不默认开启后台自动整理                   |

## 8. 验收与验证要求

### 8.1 定位正确性

- 不同时区、相机固定偏移或偏移变化、同日跨城、城市边界、同名城市、GPS 异常、稀疏锚点和缺拍摄时间均有样本；没有足够证据的项目保持未知。
- 原始 GPS、待确认推断和已接受推断在详情、地图与筛选中的含义一致；城市代表点不冒充拍摄坐标。
- 接受、拒绝、修改、撤销、重跑、替换原片和并发操作有明确状态；人工确认不被重提取或模型重跑覆盖。
- 报告城市正确率、错误建议数、建议覆盖率与人工修正量，不仅报告有多少照片被填上城市。

### 8.2 非照片判断与操作

- 正反例包含截图、海报、设计图、扫描件、普通照片、翻拍、拍到屏幕的照片、编辑成片、缺 EXIF 照片、RAW、实况及视频；边界类别单独标注。
- 在固定评估集上分别报告候选召回和最终建议的误报、漏报，以及被建议剔除的真实照片数量；阈值调试集与验收集分开。数值门槛在阶段 0 约定，不编造准确率承诺。
- 明确区分“建议剔除”和“已执行”；只对接受的实际资源生效；部分失败、取消、超时重试和组内成员操作不扩大范围。
- 回收可恢复；若开放发送，验证目标独立、源项可恢复、私密边界、失败补偿和重复调用语义。

### 8.3 安全与工程

- MCP、HTTP 和底层应用服务都验证 owner、模式、私密、回收及媒体版本；覆盖未登录、伪造计划、跨主体、跨模式、过期授权、计划篡改、提示注入和旧预览执行等负例。
- 优先复用现有测试基础设施。migration、seed、test、import 前运行 `npm run db:guard`，仅使用允许的数据库及隔离对象存储；不连接 SekerChat 或擅自访问群晖真实图库。
- 每个代码里程碑运行 lint、typecheck、unit test 和 build；通用能力变更通过 `npm run architecture:check`、共用契约及反例测试；API 变化同步生成并审查契约，认证、媒体读取与写操作补安全测试。
- 使用真实授权小样本执行模型质量评估；mock、合成向量和数据库通过只能证明链路，不能证明分类或定位准确率。真实图库扫描、备份恢复演练与上线另按明确授权安排。
- 校验有界分页、预览尺寸、请求预算、并发、任务取消及失败重试，避免挤占交互式预览和既有媒体队列。MCP 请求不能全量下载原片或触发全库向量重建。
