2026-10-26 人物扫描补齐：人物识别沿用唯一持久媒体队列、BACKGROUND 车道、租约和 FACES 暂停策略。旧图库由认证主体发起幂等全库补排，SQL 直接写入当前可见且有预览的照片版本，不将整库 ID 载入 API，不提升交互优先级；失败任务由既有重试入口处理，不重复创建。任务中心共用实现始终呈现照片人物类别和未扫描覆盖数，不能以零任务冒充已完成。扫描入口由通用任务控制器转发至 library-persistence 的摄影任务计划，既有摄影入口调用相同计划；不新增 provider、覆盖 Controller、反向导入摄影 UI 或另建执行器。用户后续已授权合并 main 并统一发布，实时发布状态见现用运行文档。

## 门禁如何工作

照片编辑沿用既有 `PhotoEditor` 与 Worker、共用上传客户端及 `EagleUploadService`；两模式只绑定路由与查询键。来源声明、私密继承和重试均进入既有上传实现，不新增照片专属保存 Controller 或并行编辑器。原编辑器的布局与像素算法保持一份。

`npm run architecture:check` 只读源码，以 TypeScript AST 检查：

- App 只装配一个共用工作区；共用瀑布流、缩略图、筛选栏、查看器及上传／编辑 hooks 各有一个装配点，不能直接放入按模式判断的分支。
- 图库只定义一份通用卡片，内部不能按模式增加日期等展示分支。无障碍标签与标题措辞允许不同；照片组角标由实际组数据决定。
- 瀑布流算法、缩略图、查看器与快捷筛选状态保持模式无关；无障碍文案允许不同。模式作用域与摄影字段可见性属于各自适配层。
- Web／API 通用 Eagle 模块不能反向导入摄影目录或摄影 API，工作区页面是显式组合入口。检查普通 import、重导出、动态 import 与 require。
- 照片的五个通用 Controller 必须保持空继承，不覆盖方法或构造函数；共用 provider 注册表必须完整复用，仅排除全局维护调度实例。新增摄影 provider 或改变注册方式须明确调整边界规则。
- 缺失必要入口、源码解析失败均报错；不是找不到文件就跳过。错误包含文件、规则和修改方向。注释中的假代码不会触发规则。

`npm run test:architecture` 用内存副本故意制造重复渲染、模式分支、日期覆盖、反向依赖、方法覆盖、服务替换、缺失入口等变化，断言门禁拒绝它们，不修改实际源文件。检查器的行、分支、函数覆盖率分别要求至少 80%。

`npm test` 另外包含两组运行时契约：

- API：确认五组 Controller 的每一个路由使用同一处理函数，照片适配器实际注册，路由／守卫元数据一致，两个模块完整且不重复地注册同一批通用 provider，并分别绑定固定模式。新增基类路由自动进入此契约。
- Web：六类客户端工厂暴露相同操作；列表／搜索、标签修改、回收／恢复、规则计数、AI 标签、向量、处理任务及隐私请求保持方法、载荷、凭据与结果语义一致，只有作用域路径不同。

这些检查保护已定义的结构与行为，不证明任意代码的语义完全等价，也不替代浏览器验收、owner／mode 隔离测试或代码评审。间接布尔变量、任意运行时动态装配、CSS 覆盖及未经列举的新能力仍需审查；不能把“门禁通过”解释为所有差异自动合理。
