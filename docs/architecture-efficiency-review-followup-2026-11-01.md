# 架构效率评审：后续修复与契约

本轮在 `codex/architecture-efficiency` 延续本地候选，修复评审中成立的问题。没有合并 main、push、生产迁移、发布或重启；现用事实不变，`current-runtime` 不修改。此前[实施记录](architecture-efficiency-results-2026-11-01.md)的3条SQL、5秒预算是前一检查点，不再代表当前清空整条操作。

## 清空回收站：后台分批，不再整库押注一个事务

最初尝试独立事务预算及数据库 LOCAL 语句时限，实库6.5秒锁等待通过，超时也能完整回滚。但六万项压力复核再次失败，故没有把“放大预算、复跑通过”当最终修复。

保留原 `EMPTY_TRASH` 操作与 purge 队列，不新增任务表／队列／检查点表。API仅受理，独立operations执行：

1. 准入持久化原operation，其 `createdAt` 固定清空cutoff，主体及私密权限仍来自认证principal。
2. `EagleService.emptyTrashBatch` 只处理一个有界步骤。PostgreSQL按id选取并锁定最多512个符合owner／mode／私密／deletedAt／purgeAfter／cutoff条件的资源，标记和当前／旧版本purge登记仍在同一CTE、同一事务内，只返回数量，ID不回到Node。
3. `purgeAfter`和原purge任务就是已提交进度。非空批次后原item回到PENDING，下一次领取继续；只有一次合法空步骤证明cutoff范围已排空，才把该item标COMPLETED。进度单位仍是一个清空命令，不伪装为已物理删除多少图片。
4. 每批写前与写后复核认证版本、私密期限和租约。失败回滚当前批次的资源、任务和事件；已成功批次保留。原操作重试／执行器重启跳过已提交资源，不重复登记；新进入回收站的资源不越过cutoff。
5. 沿用原取消语义：只取消PENDING，不打断RUNNING，取消结果以回执为准；在批次边界成功取消只停止尚未执行的工作，不撤销已经安排的永久清理。物理对象删除仍由原purge／outbox完成；终态不宣称空间已释放。失败或取消的终态仍校准回收站，不能把部分成功隐藏成全部回滚。

这是有意修订原整库单事务方案：放弃整库一次提交，换取有界持锁、可持续推进及可恢复失败。不是把一个巨大事务搬到另一个进程。

预算不是全库响应时间承诺，也不改全局Prisma默认。API与operations的基础Compose及NAS生成配置透传同样预算。原120秒租约、心跳、其他操作并发及其时限不变。入口现为快速准入，不需要扩大原15秒网关时限。

### 两个旧入口的兼容变化

`DELETE /api/eagle/trash` 与 `POST /api/eagle/trash/empty`（PHOTO继承路由同理）现在都返回 **HTTP 202 + EagleOperationSummary**，不再同步返回 `affectedAssetCount`。通过已有operations查询、结果、取消／重试端点跟进；OpenAPI同步发布202契约。现有网页／桌面已使用operations受理路径，没有新增点击或手动批次。

旧客户端若直接消费这两个入口，需要改为跟进返回的操作编号；不能把202当成物理删除完成，也不能伪造同步删除数量。重复发送旧入口会创建另一条明确命令，执行仍依原标记幂等；需要固定commandId的调用方继续使用 `POST /operations`。

### 真实失败证据与计量边界

- 前轮默认5秒的实库锁等待RED，以及本轮超时错误分类RED均保留；6.5秒锁等待、750毫秒测试语句预算回滚、同一原操作重试与发布后撤权回滚有真实数据库验证。
- 小库直接增长到六万项的测试曾产生错误外键执行计划：按owner／mode扫描索引，再按id过滤，每次过滤近五万行。诊断捕捉到实际计划，不把它统称NAS慢。测试夹具显式准备统计信息，并把这项准备排除业务计量；没有增加生产ANALYZE、planner开关、内存或全局时限。
- 最终清空即使遇到统计偏差，也不再用一条语句处理六万项。专门回归覆盖513项的首批提交、第二批失败、执行器重新实例化、原命令重试及晚进入资源保留。
- 领域步骤成本是每步4条客户端SQL（BEGIN、LOCAL预算、集合语句、COMMIT）、1事务、零S3；触发器内部仍有随资源数增长的工作。完整命令还包括准入、领取／守卫、item状态、空闲发现和实际采样的进度查询，分开报告，不能把每步4条称为整条命令4条。513项完整命令两模式实测均为：准入7SQL／1事务；3次tick各30SQL／4显式事务（含空闲车道发现、领取、原前置校验、批次发布及item写入），共90SQL／12事务；夹具每步读一次进度共9SQL／0显式事务；该采样总计106SQL／13显式事务、零S3。HTTP认证和浏览器实际轮询未计入，不能把夹具采样频率冒充浏览器频率。
- 2048项是4个非空步骤加1个空步骤，20条领域SQL／5事务；六万项是118个非空步骤加1个空步骤，476条领域SQL／119事务，最多12个绑定。Prisma连接健康探针 `SELECT 1` 另外计入实际总SQL，不能省略；不是业务重复写。一次定向样本六万项为477SQL（含1次健康探针）、119事务、单步集合语句最大624ms；同机另次最大1014ms，不作为p95或生产时限保证。耗时、WAL、NAS冷缓存及前台p95不做生产收益承诺。

## 旧 API 与新 operations 的重叠

固定提交 `89acbe96a1d9f39cd398a2dde3e239684b4f685b` 的两个旧API provider以逐字源码夹具保存并验证SHA256；只为测试编译重定位模块，不改其定时器、SQL和方法体，不依赖CI完整Git历史。新、旧各自运行在独立子进程和独立Prisma连接中。

两模式实库测试用屏障确保两个进程同时发现同一上传与维护事实，再同时放行，验证：旧60秒／10分钟定时器实际启动；上传只发布一项；旧完成任务清理而新完成／待处理任务保持；过期复制计划只登记一份outbox，HANDOFF不删除源；重复维护不重复登记；两进程关闭定时器并正常排空。它是固定旧provider与当前宿主的跨进程兼容验证，不冒充整个历史API镜像的启动验收。

该测试不授予任意版本／任意时序长期混跑的保证。尤其旧版本替换清理确认没有新版本的键快照CAS，不能声称它在同时登记新清理意图时也安全；因此升级采用实际停止旧写入者的交接，不把一次重叠测试当长期混跑许可。实际升级采用停止旧宿主后启动新版本：`deployCompose` 在迁移前停止gateway、API、worker及operations，Compose返回停止成功后才继续；停止失败不执行迁移或启动替代服务。原脚本漏停operations，已补行为反例。NAS生成脚本只生成配置，不执行部署；手动NAS发布必须同样排空旧API与operations，最终镜像冒烟仍是发布前门禁。本轮没有执行部署脚本的真实Docker变更。

## 数据库分批门禁：能证明什么

AST覆盖五个登记路径：asset-operations、duplicates、duplicate-cleanup、duplicate-index、duplicate-verification。阻止500／512裸目标、本地直接别名，以及 `OPERATION_DB_BATCH_SIZE` 导入别名及其简单本地传递别名重新用于for增量／slice。

它是旧写法回归门禁，不是全程序数据流证明。不会证明任意 `rows.slice(0,size)`、跨函数动态计算或未登记文件的参数预算正确；解码槽、预览分页等不同资源策略也不能机械套入DB预算。新增DB写路径须登记语句真实宽度和固定绑定、补真实边界测试、审查是否扩展门禁。修改命名预算或SQL字段后，仍需跑真实数据库边界；“AST通过”不等于“预算已证明”。

## 刷新协调器契约

不重新拆写协调器。已有状态各有职责：epoch隔离工作区重置，intentVersion隔离较新的用户意图，handled防止回执重复应用，destinationViews保留缺失成员补读；这些不只是装饰性状态。

1. 普通成员变更对每个活跃目的查询每轮只成功补读一次首窗口，合并而不截断原pages／pageParams；关闭的目的查询只stale、立即零GET。失败的一轮可按既有策略有限重试，不能把“最多一次”解释成失败也禁止重试。EMPTY_TRASH终态无逐成员回执，是校准所有已加载回收站页的明确例外，十二页即十二GET，不冒充零刷新。
2. 补读前先取消旧原查询，再stale，旧响应不得覆盖新合并。工作区epoch变化或查询已替换时不得写回旧结果。
3. 失败保留目的意图，下次明确schedule／终态事件再试；已应用回执不重读，不在本轮失败时自旋。每轮摘取独立目的快照，后到的同view终态留给下一轮，不能被旧成功清掉。

对应 `asset-operation-refresh.test.ts`：active trash first window、failed destination、older in-flight infinite response、second destination intent；均包含十二页／pageParams事实断言。`.catch(() => undefined)`不能据此删除待重试意图，也不能把未校准显示为已校准。这个契约及运行用例共同约束后续修改，不凭291行就再次造一层刷新框架。
